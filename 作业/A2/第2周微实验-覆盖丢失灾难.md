## 二、实验设计

### 2.1 为什么不能"编"一个灾难

覆盖丢失的危险性不在于"文件没了"，而在于：

> **它不报错。** 没有任何提示告诉你丢了东西。你会以为一切都好。

所以本实验必须**真实制造一次丢失**，并记录下"丢失时是什么都没发生"这个事实。
摆拍式的演示无法体现这一点。

### 2.2 实验对象的选择

选用一段与本项目同源的规则函数（`养成.js` 风格的经验结算）：

```javascript
// 养成规则层 · 经验结算
function 结算经验(打卡) {
  var 经验 = 0;
  if (打卡.早餐) 经验 += 20;
  if (打卡.午餐) 经验 += 20;
  经验 += 打卡.喝水 * 5;
  return 经验;
}
```

起点 SHA256：`A3AD2C7AD09A60BB…`

## 三、实验组：乱保存导致的覆盖丢失

### 3.1 三次改动，两个版本名

**改动 1**：加入晚餐打卡 `+20`。

存盘时的自然反应——"多存几份更安全"：

```powershell
Copy-Item '养成规则.js' '养成规则_最终版.js'
Copy-Item '养成规则.js' '养成规则_最终版_v2.js'
```

此时三个文件指纹完全相同，**看起来很安全**：

| 文件 | 指纹（前 16 位） |
|---|---|
| 养成规则.js | `067CCA03245EBC13` |
| 养成规则_最终版.js | `067CCA03245EBC13` |
| 养成规则_最终版_v2.js | `067CCA03245EBC13` |

**改动 2**：加入"一日达标 +50"奖励，**只存进主文件，没有更新副本**。

这是真实开发中最常见的疏漏。此时的真实状态：

| 文件 | 是否含 `+50` |
|---|---|
| 养成规则.js | ✅ **有**（真正最新） |
| 养成规则_最终版.js | ❌ 无 |
| 养成规则_最终版_v2.js | ❌ 无 |

> **第一个陷阱**：名字最像"最终答案"的那个文件（`_最终版_v2`），**已经落后了一个版本**。
> 文件名制造了一种虚假的安全感。

### 3.2 灾难发生

一个月后回来，以为 `_最终版_v2.jar` 是最新的，把它拷回主文件：

```powershell
Copy-Item '养成规则_最终版_v2.js' '养成规则.js' -Force
```

**实测输出：**

```
覆盖前 养成规则.js 指纹 = E997DE6DAC1BC64557327645348550D33697315B2D1D30777DEEBEAB0A068513
覆盖后 养成规则.js 指纹 = 067CCA03245EBC13741037C19789C12EE5319F29B02575985D61A98F4C9015E5

>>> 指纹不同：改动已丢失

「一日达标 +50」这条逻辑还在吗
>>> 已永久丢失，而且找不到任何记录
```

### 3.3 关键观察：整个过程没有任何提示

| 时刻 | 系统反馈 |
|---|---|
| 覆盖文件 | 无提示 |
| 覆盖完成 | 无提示 |
| 打开文件 | 内容看起来**完全正常**（语法正确、函数完整） |
| 跑起来 | **能正常运行**，只是少了 50 经验 |

**这就是覆盖丢失最危险的地方：它伪装成了一个健康的状态。**

### 3.4 事后状态：三个文件全都"一样"

| 文件 | 大小 | 含量 | 指纹前 12 位 |
|---|---|---|---|
| 养成规则.js | 242 B | ❌ 无 +50 | `067CCA03245E` |
| 养成规则_最终版.js | 242 B | ❌ 无 +50 | `067CCA03245E` |
| 养成规则_最终版_v2.js | 242 B | ❌ 无 +50 | `067CCA03245E` |

**三个文件指纹完全一致**——如果有谁用"文件都一致"来判断安全性，会得出"没有问题"的结论。
但真实情况是：**三个副本全都是过期的，最新的那一版已经不存在于任何地方。**

### 3.5 为什么文件名救不了你

| 想知道的 | 文件名能回答吗 |
|---|---|
| 当前哪份最新？ | ❌ 需要逐个打开对比 |
| 上次改了什么？ | ❌ **完全没有记录** |
| 谁在什么时候改的？ | ❌ 只有文件修改时间，且拷来拷去会乱掉 |
| 丢掉的内容能找回来吗？ | ❌ **不能** |

## 四、对照组：同样的三次改动，用 Git 做

### 4.1 独立仓库，同样的起点

```powershell
git init
git add 养成规则.js && git commit -m "基线：经验结算初版"
# 改动一
git add 养成规则.js && git commit -m "功能：经验结算加入晚餐打卡"
# 改动二
git add 养成规则.js && git commit -m "功能：三餐全打卡额外奖励 50 经验"
```

**实测历史：**

```
0750232 功能：三餐全打卡额外奖励 50 经验
ffb3781 功能：经验结算加入晚餐打卡
309ae69 基线：经验结算初版
```

### 4.2 施加同样的"破坏"

把旧版（两个提交之前）的内容拷回工作区：

```powershell
git checkout HEAD~2 -- 养成规则.js
```

**实测：**

```
$ git status
M   养成规则.js          ← 立刻告诉你"这个文件被改了"

$ 检查是否含 +50
工作区里没了
```

**注意第一个差别**：Git **主动告诉你工作区被改动了**；
而乱保存的 `Copy-Item` 什么都不会说。

### 4.3 完整找回

```powershell
git checkout HEAD -- 养成规则.js
```

**实测：**

```
>>> 已完整找回
```

### 4.4 两边的对比

| | 乱保存 | Git |
|---|---|---|
| 覆盖后有无提示 | ❌ 无 | ✅ `git status` 显示 `M` |
| 能否恢复到覆盖前 | ❌ **不能**（内容永久丢失） | ✅ `git checkout` 一条命令 |
| 能否查"上次改了什么" | ❌ 无 | ✅ `git diff` / `git log` |
| 副本是否会自动一致 | ❌ 会各自漂移 | ✅ 单一事实来源 |
| 需要手工维护副本吗 | ✅ 需要（这就是问题来源） | ❌ 不需要 |

## 五、真实案例验证：本项目自己的历史

上面的实验是模拟的。本节用**仓库中真实发生过的事**再验证一次。

### 5.1 事件

`自选作品/养成系统-方案-v2.md`（227 行设计稿）曾在提交 `094accc` 中被引入，
后在提交 `6506fee` 中被 `养成系统-方案-v3.md` 取代。

> 口径说明：`git show --stat 6506fee` 显示该文件的变更为 **326 行删除**，
> 而按行统计文件内容为 **227 行**。两者不矛盾——`--stat` 统计的是 diff 行数
> （含文件末尾换行差异等），不是文件行数。本文件统一使用 **227 行**（文件实际行数）。
> 校验命令：`git show 094accc:自选作品/养成系统-方案-v2.md | Measure-Object -Line`

### 5.2 现状与验证

```powershell
$ Test-Path 自选作品/文档/养成系统-方案-v2.md
>>> 没有，文件已不在工作区

$ git show 094accc:自选作品/养成系统-方案-v2.md | Measure-Object -Line
>>> v2 原始行数 = 227
```

**取回的原文片段：**

```
# 养成系统 · 方案 v2（评审稿）

日期：2026-11-16 ｜ 目标作品：`自选作品/`（食谱搭配 v0.5.0，7 页纯前端、零依赖、断网可跑）
基础稿：`养成系统-实现规格.md`（DeepSeek 版 v0.6.0）
本文件只做三件事：**判断原稿能不能用 → 列出必须改的地方 → 回答 3D 可行不可行**。
```

### 5.3 这个案例说明了什么

| 事实 | 意义 |
|---|---|
| 工作区里已经**没有** v2 文件 | 确实"丢"了 |
| 但 227 行原文**完整可取回** | Git 记录的是快照，不是"最新副本" |
| 而且能精确指出在哪个提交里 | 可追溯到具体决策点 |

**这跟第三节的区别是本质性的**：第三节那些 `_最终版` 文件一旦被覆盖，**没有任何地方存着旧内容**；
而 Git 里的"删除"只是"当前快照里没有它"，历史快照仍然完整。

## 六、结论

### 6.1 核心结论

> **文件名不是版本控制。**
> `最终版`、`_v2`、`_真的最终`、`_修改_2026-11-24` —— 这些命名
> **无法回答"上次改了什么"**，因为它们没有历史。
> 它们只在"我还记得哪份是最新的"这个前提成立时才有用，而这个前提总会失效。

### 6.2 三个可迁移的教训

**1. 覆盖丢失不报错，这是它最危险的地方**

本实验中，覆盖发生后：文件语法正确、函数完整、程序能跑。**唯一的异常是少了一条业务逻辑**，
而这条逻辑是否该存在，只有作者记得。

**2. "多存几份"制造的是虚假安全感**

存了 3 份副本，最终 3 份**全部过期且互相一致**。副本数量不等于安全性，
**副本之间一旦失去同步，多出来的只是错误答案**。

**3. 能否恢复，取决于"存过什么"，不是"存了几份"**

乱保存：3 个文件，0 份历史 → 丢了的找不回。
Git：1 个工作文件，N 份快照 → 任意时刻都能回到任意一次提交。

### 6.3 与 A2 已有结论的衔接

A2 的 [5.6 节](A2-交付说明.md) 已经发现一个相关问题：

> `逻辑复算.py` 在 `脚本.js` 被删掉函数后依然 106 项全绿——因为它不加载真实 JS，
> 而是把算法翻译成 Python 独立实现。**测试绿不能证明文件没坏。**

本实验是同一方法论的另一面：

| | A2 5.6 节 | 本实验 |
|---|---|---|
| 表面现象 | 测试全绿 | 三个副本文件一致 |
| 真实状态 | 文件已损坏 | 内容已丢失 |
| 靠什么识破 | SHA256 指纹 | git 历史记录 |

**两次都是"看起来很正常的坏状态"。**

### 6.4 落地到本项目的规则

基于本实验，本仓库应遵守以下四条：

| # | 规则 | 当前是否已写入 `AGENTS.md` |

| 1 | **不用文件名管理版本**：不出现 `xxx_最终版.js`、`xxx_v2.js` 这类文件 | ❌ **尚未写入**（本次核对确认） |
