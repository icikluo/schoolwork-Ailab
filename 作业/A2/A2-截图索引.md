## 一、快照状态理解（评分点①，2 分）

对应文档第二节「快照状态理解」。

| 文件 | 内容 | 证明了什么 |
|---|---|---|
| `A2-01-状态一-干净.png` | `git status` 输出「nothing to commit, working tree clean」 | 三区内容一致时，没有任何改动待处理 |
| `A2-02-状态二-已修改未暂存.png` | `git status` 输出「Changes not staged for commit」 | 工作区有新改动，但还没进暂存区 |
| `A2-03-diff-工作区vs暂存区.png` | `git diff` 输出的红绿对比 | **`git diff` 能看到工作区与暂存区的差异** |
| `A2-04-状态三-已暂存未提交.png` | `git status` 输出「Changes to be committed」 | 改动已进暂存区，等待提交 |
| `A2-05-diff-工作区vs暂存区-应为空.png` | `git diff` 无输出 | **暂存后工作区与暂存区已一致，所以 diff 为空** |
| `A2-06-diff-cached-暂存区vs版本库.png` | `git diff --cached` 输出红绿对比 | **`--cached` 能看到暂存区与版本库的差异** |

### 这组截图的核心价值

**A2-03 和 A2-05 放一起看，能一眼看懂三分区**：

```
状态二时：git diff 有输出   （工作区 ≠ 暂存区）
   ↓ git add
状态三时：git diff 无输出   （工作区 = 暂存区）
          git diff --cached 有输出（暂存区 ≠ 版本库）
```

同一份改动，`git add` 前后两个命令的输出**正好相反**——
这就是「暂存区是一个真实存在的中间层」最直接的证据。

## 三、差异与验证（评分点③，2 分）

对应文档第四节「一个真实的逐行审查发现意外案例」。

| 文件 | 内容 |
|---|---|
| `A2-03-diff-工作区vs暂存区.png` | 展示 `git diff` 的实际输出格式（红删绿增） |

### 该案例的核心

修改 README 里两处数字，**看起来只需要两行改动**。
但逐行审查 `diff` 时发现第一行也变了：

```diff
-# 🥗 食谱搭配
+﻿# 🥗 食谱搭配     ← 开头多了看不见的 UTF-8 BOM
```

**如果直接提交，这个 BOM 变化会永远留在历史里，且日后无法解释是谁为什么改的。**

完整过程见交付说明 4.1 节。

### 验证顺序

先跑测试确认事实（99 项），再改文档写 99——
**不是先写 99 再找理由**。

```

验证 2：计算目标卡路里() 已恢复    → 函数回来了
验证 3：被测文件无未提交改动       → git status 不再显示该文件
```

## 六、一键复现

想自己验证这些截图的内容，可在仓库根目录执行：

```bash
# 三态
git status                    # 干净
echo "test" >> 自选作品/README.md
git status                    # 状态二
git diff                      # 看得到差异
git add 自选作品/README.md
git diff                      # 空
git diff --cached             # 看得到差异
git restore --staged --worktree -- 自选作品/README.md   # 复原

# 受控恢复
git restore --worktree --source=HEAD -- 自选作品/脚本.js
```
