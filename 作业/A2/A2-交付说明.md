## 二、评分点一：快照状态理解

### 2.1 三个区是什么

Git 里的一个文件可以同时存在于**三个地方**，各有独立内容：

```
工作区（Working Directory）   你打开、编辑的那个文件
        ↓ git add
暂存区（Index / Staging）     下一次提交要包含的快照
        ↓ git commit
版本库（Repository / HEAD）   已经提交的历史
```

**关键点：三处内容可以各不相同。**

| 区域 | 类比 | 命令查看差异 |
|---|---|---|
| 工作区 vs 暂存区 | 我现在改的 vs 准备提交的 | `git diff` |
| 暂存区 vs 版本库 | 准备提交的 vs 上次提交的 | `git diff --cached` |
| 工作区 vs 版本库 | 我现在改的 vs 上次提交的 | `git diff HEAD` |

### 2.2 实测：三种状态

#### 状态一：干净（三处完全一致）

```
$ git status
On branch main
nothing to commit, working tree clean
```

此时工作区 = 暂存区 = HEAD，三处内容相同。

#### 状态二：已修改、未暂存（工作区 ≠ 暂存区）

修改 `自选作品/README.md`，把测试项数从 81 改成 99：

```
$ git status
On branch main
Changes not staged for commit:
        modified:   自选作品/README.md
```

此时：
- **工作区** = 新内容（99 项）
- **暂存区** = 旧内容（81 项）
- **版本库** = 旧内容（81 项）

`git diff` 能看到这个差异。

#### 状态三：已暂存、未提交（暂存区 ≠ 版本库）

执行 `git add` 之后：

```
$ git status
On branch main
Changes to be committed:
        modified:   自选作品/README.md
```

此时：
- **工作区** = 新内容
- **暂存区** = 新内容（已被 `git add` 更新）
- **版本库** = 旧内容

**验证方式**：

```
$ git diff
（无输出 —— 说明工作区与暂存区一致）

$ git diff --cached --stat
 自选作品/README.md | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)
```

**这两个命令输出相反，正好证明了三分区的存在**：
`git diff` 空、`git diff --cached` 非空，说明改动已经进了暂存区但还没进版本库。

### 3.4 一个反面例子（已记录）

早期有一条提交改动了 **25 个文件**：

```
0e47641  功能：为食谱配备本地化图片，经验证后 22/24 条有图
```

这条提交同时做了：新增数据字段、改数据文件、新增 22 张图片、改测试脚本。

**为什么要分开**：如果后来发现某张图片配错了，想只回退那张图，
因为数据和代码混在一起，`git revert` 会把整个提交都撤掉。

**改进**：之后的图片相关提交拆得更细了（如 `e56b72e` 只补 2 张图）。

### 3.5 为什么不用 `git commit -a`

`git commit -a` 会把工作区所有改动一次性提交，
**等于放弃了对「这次提交到底包含什么」的控制权**。

本仓库从未使用 `-a`，每次都显式 `git add` 指定文件。

## 四、评分点三：差异与验证

### 4.1 一个真实的「逐行审查发现意外」案例

#### 背景

任务：把 README 里过时的「81 项测试」改成「99 项」。

看起来是个两处替换的小改动，**不审查直接提交也"没问题"**。

#### 实际执行后看 diff

```diff
@@ -1,4 +1,4 @@
-# 🥗 食谱搭配
+﻿# 🥗 食谱搭配

@@ -48,7 +48,7 @@
-    ├── 逻辑复算.py      复算公式、汇总、推荐、一周计划、宏量目标与功能增强（81 项测试）
+    ├── 逻辑复算.py      复算公式、汇总、推荐、一周计划、宏量目标与功能增强（99 项测试）
```

**第一行出现了意外改动。**

`# 🥗` 变成了 `🥗` —— 开头多了一个**看不见的字符**。

#### 定位

用 Python 读文件头字节：

```python
raw = Path("README.md").read_bytes()
print(raw[:3])   # b'\xef\xbb\xbf'  ← UTF-8 BOM
```

确认是多了一个 **UTF-8 BOM**（字节序标记）。

**原因**：之前用 Windows PowerShell 的 `Set-Content` 编辑文件时，
它默认会写入 BOM。而 Git 仓库里存的是无 BOM 的版本。

#### 处理

用 Python 显式读写，去掉 BOM：

```python
s = p.read_text(encoding="utf-8-sig")   # 读时自动剥掉 BOM
p.write_text(s, encoding="utf-8", newline="\n")   # 写时不带 BOM
```

#### 修复后的 diff

```diff
@@ -48,7 +48,7 @@
-    ├── 逻辑复算.py      ...（81 项测试）
+    ├── 逻辑复算.py      ...（99 项测试）

@@ -61,7 +61,7 @@
-python 测试/逻辑复算.py     # 81 项：...
+python 测试/逻辑复算.py     # 99 项：...
```

**只有预期中的两处改动。**

#### 这次审查的意义

如果直接 `git add && git commit`：
- 提交里会夹带一个 BOM 变化
- 在 diff 里显示成「第一行被重写」，但看不出为什么
- 日后排查「这行什么时候被改的」会一头雾水

**逐行审查 diff 的价值就在这里：它让你发现"你没打算改、但它变了"的东西。**

### 4.2 验证改动是否正确（不只是看得对）

改完文档后不能只看 diff 顺眼，还要验证内容**在事实上正确**：

```bash
$ python 测试/逻辑复算.py
通过 99 项，失败 0 项        ← 实测就是 99 项，与 README 写的一致
```

**顺序很重要**：先验证事实（实测 99 项），再改文档写 99。
反过来（先写 99 再验证）就成了"照着自己想的写"。

### 5.4 三种恢复方式对比

Git 有三种「撤销」方式，**语义完全不同，不能混用**：

| 命令 | 影响范围 | 用途 | 危险度 |
|---|---|---|---|
| `git restore --worktree <file>` | 只恢复**工作区**某个文件 | 丢弃未提交的修改 | 🟢 低（改动还没提交，丢了就是丢了） |
| `git restore --staged <file>` | 只把文件**移出暂存区** | 撤销 `git add`，工作区内容不变 | 🟢 低 |
| `git revert <commit>` | 生成一个**新的反向提交** | 撤销已提交的历史 | 🟢 低（历史保留） |
| `git reset --hard` | 同时重置工作区+暂存区+HEAD | 彻底丢弃 | 🔴 **高（不可恢复）** |

**本作业选择 `git restore --worktree` 的理由**：

1. **精确**：只影响指定文件，不波及其他改动
2. **非破坏性**：不改变提交历史，只是把工作区恢复成 HEAD 的样子
3. **可预见**：结果一定是「该文件与上次提交完全相同」

### 5.5 一个容易混淆的点

执行 `git restore --worktree` 后，如果**暂存区里已经有该文件的新版本**，
恢复出来的会是**暂存区的版本**，不是 HEAD 的版本。

本例中我用了 `--source=HEAD` 显式指定来源，避开了这个歧义。

**这意味着**：`git restore` 的目标是「让工作区 = 某个来源」，
默认来源是暂存区，而不是版本库。

> **一个必须如实写下的发现**：本次复核还发现——
> **`逻辑复算.py` 在 `脚本.js` 被删掉函数后依然 106 项全绿。**
> 原因是该脚本不加载真实 JS，而是把算法**翻译成 Python 独立实现**再复算，
> 所以在「脚本被改坏、但 Python 副本没改」时，它**检查不出问题**。
> 这不是缺陷（它的定位是数值复算，不是语法/运行检查），但对 A2 有直接影响：
> **「恢复后跑测试通过」只能证明数值逻辑对，不能证明文件还原成功**——
> 真正起证明作用的是 SHA256 指纹。这一点比原 5.2 节的表述更准确，记在此处。

## 七、实践中踩到的坑（诚实记录）

| 坑 | 现象 | 应对 |
|---|---|---|
| **BOM 污染** | PowerShell 编辑后多了看不见的 UTF-8 BOM | 用 Python 显式指定编码读写；或在编辑器里设置「UTF-8 无 BOM」 |
| **`git restore` 分不清对象** | 以为恢复工作区就会恢复一切 | 记住默认来源是**暂存区**，要 HEAD 得加 `--source=HEAD` |
| **恢复后没验证** | 恢复命令返回 0 就以为万事大吉 | 必须跑测试 + 比对指纹 |
| **一次 `git add -A` 夹带临时文件** | 曾把 `commit_msg.txt` 误提交 | 改为每次明确指定文件路径 |
