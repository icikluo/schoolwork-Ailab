## 二、评分点一：共同基线（2 分）

### 2.1 基线是什么

在两条分支开出**之前**，先在 `main` 上提交了 `2d2b879`，并打 tag `a3-baseline`：

| 文件 | 作用 |
|---|---|
| `作业/A3/A3-方案选型标准.md` | 共同基线定义、接口契约、四项指标与权重、淘汰门槛、平票裁决、预设差异与**预测** |
| `自选作品/数据/商店.js` | 商品表（零食 5 币/每日上限 3；玩具 8/2）。两分支共用，**不得修改** |
| `自选作品/养成商店.js` | `结算购买()` 的**契约空壳**：签名与返回结构固定，函数体抛异常 |
| `自选作品/测试/核对商店.py` | 22 项契约检查（数据契约 / 结构约束 / 规则层禁碰 DOM / 返回字段） |
| `自选作品/测试/基准商店.py` | 统一基准：静态统计 + JS 语义子集翻译 + 459 条穷举对拍 + P95 耗时 |

### 2.2 为什么基线要先于实现

- **预期先于实现**（课程第 10 周主题的提前演练）：基线上 `基准商店.py` **必然失败**（空壳抛异常）。
  这是刻意留下的红灯——两分支各自让它转绿，才能证明"是分支实现的功劳"。
- **接口先于实现**（第 5 周主题）：返回结构 `{ 存档, 每日, 结果, 价格, 剩余金币 }` 在基线里就定死了，
  两分支只能实现不能改契约，否则比较无意义。
- **数据先于实现**：商品价格与每日上限放进 `数据/商店.js`，两分支都从同一份数据读，
  杜绝"某分支偷偷调价让自己的用例更漂亮"。

### 2.3 基线验证

```text
$ python 测试/核对商店.py
通过 22 项，失败 0 项

$ python 测试/基准商店.py --方案 基线
【失败】结算购买 抛出异常：Error: 结算购买 尚未实现   ← 预期中的红灯
```

> **2026-11-24 复核实测（报错信息与原文不同，如实记录）**：
> 在 `2d2b879` 的干净 worktree 上重跑 `--方案 基线`，实际输出是
>
> ```text
> 【失败】结算购买 抛出异常：NameError: name '查道具' is not defined
> ```
>
> **退出码仍为 1，红灯成立**——但报的错误**不是**预期的 `Error: 结算购买 尚未实现`。
>
> **原因**：基线的 `养成商店.js` 只有抛出异常的空壳，此时 `查道具()` 这个辅助函数**还不存在**
> （它是方案 A 才引入的）。而 `基准商店.py` 的 JS 语义翻译器会先尝试解析并翻译实现里
> 引用的同级辅助函数（见该文件第 478 行注释），在翻译阶段就找不到 `查道具`，
> 于是**先抛出 `NameError`，根本没执行到那句 `throw`**。
>
> **这个差异说明什么**：基准器的"红灯"有效，但它对**基线空壳**的报错不够友好——
> 读者看到 `查道具 is not defined` 会误以为基准器本身坏了，而不是"基线按预期没实现"。
> 这是一个**健壮性问题**，不属于本次作业的修复范围，记录在此备查。
> **结论不变**：基线在统一基准上必然失败、两分支都必须让它转绿，这一纪律仍然成立且已实测。

## 三、评分点二：方案差异与标准（2 分）

### 3.1 两套方案的差异（不是换个写法，是换一种结构）

| | 方案 A `feature/plan-a` | 方案 B `feature/plan-b` |
|---|---|---|
| 提交 | `25c7c32` | `a71dd92` |
| 结构 | **查表式**：`查道具()` 线性查找 → 三段平铺 `if` 依次返回 | **分派表式**：`建索引()` O(1) 取价 → `判定()` 把结论归一成一个字符串 → `分派 = {"已购买": 执行购买}`，拒绝分支共用一条返回 |
| 返回语句 | 4 处（每种结果各一处） | **1 处**（结论不同、返回结构相同） |
| 扩展方式 | 新增拒绝原因要加一个 `if` | 新增拒绝原因只需在分派表加一项 |
| 代码形态 | 直白、长、分支多 | 抽象一层、短、分支少 |

### 3.2 评价标准（写于实现之前）

| # | 指标 | 权重 | 测量方法 |
|---|---|---|---|
| 1 | 正确性 | 40% | `基准商店.py` 459 条穷举用例，**一条都不能错**（硬门槛） |
| 2 | 可读性与可维护性 | 20% | 净代码行数 + 最大嵌套深度（静态统计，越少越好） |
| 3 | 性能 | 20% | P95 耗时（459 次调用归一化） |
| 4 | 可测试性 | 20% | 必须能被 Python 纯函数对拍（基线门槛） |

### 3.3 淘汰门槛（任一项不满足直接出局）

正确性 100% / 不修改入参 / 规则层不碰 DOM 与 localStorage / 六测试全绿 / 与 2.2 契约字段完全一致。

### 3.4 为什么权重这样定

- **正确性 40%**：功能错了，其他全无意义。
- **可读性 20%**：规则层代码要被人逐行审阅（课程 5 阶段证据链的"人类审查"环节），
  这是本项目真实存在的审阅成本。
- **性能 20%**：每次购买只调一次，性能差异对体验无影响；但仍给权重，是为了检验
  **"分派/索引这类结构改造能不能带来真实收益"**——如果性能没优势，抽象就缺少理由。
- **可测试性 20%**：v3 分层约束的硬要求，是"能不能被证据验证"的前提。

### 3.5 平票裁决顺序（事先定好，避免事后找理由）

正确性 → 可读性 → 性能 → 代码更短者 → 先提交者。

### 3.6 预设差异与预测（写于实现之前，事后核对）

标准第 4 节预先登记了猜测：

> 「方案 A 可读性差一些但代码最短；方案 B 若使用带状态的 `/g` 正则，会在第 2 次及以后购买时出现错误。
> 预期 A 胜出。」

**事后核对结果（诚实记录）**：

| 预测 | 结果 |
|---|---|
| A 代码更短 | ✅ 成立（23 行 vs 25 行） |
| A 可读性"差一些" | ❌ **不成立**——A 的嵌套深度 3 < B 的 4，实际更好读 |
| B 用 `/g` 正则会出错 | ❌ **未验证**——B 实际用的是分派表，没用正则，正确性无差异 |
| 预期 A 胜出 | ✅ 成立（但理由与预测不同） |

> 预测落空本身是有价值的记录：**说明"预期 B 会更优雅"的直觉是错的**，
> 分派表在只有 3 种拒绝原因时属于过度抽象。

## 六、本次实验的额外收获（教学价值）

### 6.1 最大的工作量不在被测代码，而在"统一基准"

为了让"两套方案"真正可比，必须有一个能把两分支的 JS 实现**翻译成 Python 再对拍**的基准器
（`测试/基准商店.py`，约 700 行）。被测代码本身只有 23–25 行。

基准器踩到的坑（都写在文件注释里）：

| 坑 | 现象 | 教训 |
|---|---|---|
| `类` 变量遮蔽 | 把 token 类型解包进名为 `类` 的变量，覆盖了外层的 `set`，错误伪装成"无法解析语句" | 解析器里命名要避开外层变量 |
| 对象字面量里放匿名函数 | 分派表 `{"已购买": function(){...}}` 的写法让解析器越界 | 统一的"语义子集"必须预先划定 |
| `i++` / 三元 / 空对象 `{}` / `.length` | 逐一踩到，逐一补 | JS 子集边界是**被测代码的形状**决定的 |
| 属性访问的读/写语义 | 读要 `_取()`（缺键返回 None），写必须 `obj[k]=...` | 生成式翻译必须区分左值与右值 |

**结论：评测基础设施比被测代码更难写，也更值钱。** 这是本次实验最值得记住的一句。

### 6.2 标准先行的作用

B 的圈复杂度（8）比 A（10）低。如果没有事先把圈复杂度列为**参考项**、把净行数与嵌套深度列为**评分项**，
"B 更简洁"很容易被拿来当作选 B 的理由。**先定标准，再改代码**，能挡住这种事后合理化。

### 6.3 与后续作业的衔接

- 本次下沉的 `结算购买()` 还**没有接入 UI**（`养成.html` 里的 `买道具()` 仍走原逻辑）。
  接入属于**范围变更**，按 PRD「六之二」流程走，放到 A5（范围控制与集成）中处理。
- A4 要做的"接口 Schema 契约"，其实就是本作业 2.2 节那张返回结构表的正式版。
