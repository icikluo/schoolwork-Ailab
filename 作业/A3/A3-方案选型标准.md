# 方案选型标准（A3）—— 先定标准，再看结果

> 用途：课程第 4 周「双分支方案决斗」的核心纪律——**评价标准必须由人类预先制定**，
> 不能等两套方案写完之后再"自己挑一个顺眼的"。
> 本文件在任何实现代码之前写成并提交（见 git 历史：`A3 基线：公共基线与选型标准`）。

---

## 一、共同基线

| 项 | 内容 |
|---|---|
| 需求 | 宠物商店「买道具」的扣币与背包计数逻辑（`养成.html` 内的 `买道具`） |
| 现在的问题 | 商店价格与购买规则**硬编码在 `养成.html` 的渲染层**，且 `养成.html` 是 `工具/生成养成页.py` 装配出来的产物。这违反 v3 方案的分层约束（规则层 `养成.js` 不碰 DOM），也导致：① 价格无法被 Python 测试对拍；② 改价格必须改产物（违反"产物不手改"）；③ 无购买次数上限，存在"连点刷亲密"风险 |
| 变更范围 | 只动"商店价格与购买结算"这一件事；不动 3D、不动打卡、不动宠物心情 |
| 共同输入契约 | 见第二节 |

## 二、两套方案必须共同满足的接口契约（先于实现确定）

### 2.1 数据契约（新增 `数据/商店.js`，两分支内容完全一致）

```js
window.商店数据 = {
  "道具": [
    { "id": "零食", "价格": 5,  "每日上限": 3 },
    { "id": "玩具", "价格": 8,  "每日上限": 2 }
  ]
};
```

约束（两分支都必须通过 `测试/核对商店.py` 的 A 组检查）：
- 价格为正整数，`零食` 5、`玩具` 8（沿用现有硬编码值，不借机调价）
- 每日上限为正整数
- 道具 id 与 `素材/商店方案.js` 中出题器的 `买` 参数一致（`零食` / `玩具`）

### 2.2 纯函数接口（规则层，两分支函数签名与返回值结构必须一致）

```js
window.养成系统.结算购买(存档, 每日, 道具id, 额外) -> 结果对象
```

返回结构（字段名与类型固定，**两分支都必须一致**）：

```js
{
  "存档": {...},        // 新存档副本，不修改入参
  "每日": {...},        // 新的每日副本，含"购买"计数
  "结果": "已购买" | "金币不足" | "已达上限" | "无此道具",
  "价格": 5,            // 本次价格；失败时也返回该道具价格（无此道具为 0）
  "剩余金币": 42        // 结算后的金币数
}
```

**共同验证门槛（Python 门槛用例，两分支同一套期望值）**：
1. 金币足够 → `已购买`，金币减去价格，背包 +1，当日该道具购买数 +1
2. 金币不足 → `金币不足`，存档与每日都**不落盘**（数值不变）
3. 达到每日上限 → `已达上限`，数值不变
4. 非法道具 id → `无此道具`，不抛异常
5. 不修改入参对象（不可变性）
6. 不依赖 `/g` 正则的状态（本契约避免写状态型正则）

## 三、评价标准（加权指标，先定权重）

| # | 指标 | 权重 | 测量方法 | 说明 |
|---|---|---|---|---|
| 1 | **正确性** | 40% | `测试/基准商店.py` 跑 150 条穷举用例，**一条都不能错** | 硬性门槛：< 100% 直接淘汰 |
| 2 | **可读性与可维护性** | 20% | 新增/改动的**净代码行数** + **嵌套深度**（用 `测试/基准商店.py` 静态统计），越少越好 | 规则层要能被人类逐行审阅 |
| 3 | **性能** | 20% | `基准商店.py` 跑 3000 次调用取 P95 耗时（归一化到 Python 复刻） | 规则层每次购买只调一次，量级差异不影响体验，但体现算法结构 |
| 4 | **可测试性** | 20% | 必须能被 `核对商店.py` 以纯函数方式对拍，不需要浏览器 | 这条是 v3 分层的核心诉求 |

### 3.1 淘汰门槛（任一项不满足直接出局）

| 门槛 | 判定 |
|---|---|
| 正确性 = 100% | 150 条用例全过 |
| 不修改入参 | 不可变性检查通过 |
| 规则层无 DOM / localStorage 引用 | 静态扫描：新增代码块里不得出现 `document`、`localStorage`、`window.` |
| 六个既有测试全绿 | 不得破坏任何既有功能 |
| 与共同接口契约一致 | 函数名、返回结构字段必须与 2.2 完全一致 |

### 3.2 平票时的裁决顺序

1. 正确性（都已 100%，跳过）
2. 可读性
3. 性能
4. 若仍相同 → 取**代码更短**者；再相同则取**先提交**者（避免"事后改标准"）

## 四、两套方案的预设差异（写入分支之前先声明猜测，事后核对）

这是课程「问题与预测」环节的落点：**先写下预测，再用数据打脸或验证**。

| 方案 | 预先声明的实现思路 | 预测 |
|---|---|---|
| **A · 查表式** | 用 `商店数据` 数组 + `查道具()` 线性查找；结算里平铺三段 `if`（金币不足 / 上限 / 正常）；用 `find` + 解构 | 可读性差一些（三段 if），但代码最短；性能 O(n)，n=2 可忽略 |
| **B · 单匹配正则** | 用一条**带状态**的 `/g` 正则或对象字面量 `switch` 做分派；先"归一化"再统一处理 | 主观上"更优雅"，但 **`/g` 正则会因 `lastIndex` 残留导致偶发错误** —— 这正是本方案要暴露的隐患 |

> **预测性假设**：方案 B 若使用 `/g` 正则，会在**第 2 次及以后**购买时出现错误；
> 若改为无状态写法，则性能与 A 基本持平、可读性无明显优势 → 预期 **A 胜出**。
> 这个假设必须用基准数据验证或推翻，不能直接写结论。

## 五、协作纪律（本周「外科手术式团队」的落点）

1. 两分支**从同一基线 tag `a3-baseline` 开出**，base 必须在报告中写明 commit。
2. 两分支**不共享实现**：各自独立写，不得把 A 的代码复制到 B 再改名。
3. `测试/基准商店.py` 与 `测试/核对商店.py` 写在基线上，**两分支都必须通过**，不许为了迁就实现改测试期望。
4. 每个分支只做一件事，提交信息写清「问题 / 原因 / 修复（实现）/ 验证」。
5. 合并前必须把分支**rebase 到最新 main**（`git merge --no-ff` 合并），保证历史图可读。
6. 丢弃的方案**保留分支名与报告结论**，不删除远程分支，便于复核。
