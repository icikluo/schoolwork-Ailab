# A3 方案对比与取舍记录

> 课程：人机协同编程与工作流基础 · 第 4 周「一个想法，能不能保留两种做法？」
> 实验：同一需求（宠物商店购买结算）在两条特性分支上分别实现，按**预先设定**的标准评审后取舍。
> 标准见 [`A3-方案选型标准.md`](A3-方案选型标准.md)（先于实现写定并提交）。

---

## 一、共同基线

| 项 | 内容 |
|---|---|
| 基线提交 | `2d2b879`（tag `a3-baseline`） |
| 两条分支的起点 | 同一提交 `2d2b879`，`git merge-base` 可验 |
| 契约空壳 | `自选作品/养成商店.js` 里的 `结算购买()`，签名与返回结构在基线里已固定 |
| 数据契约 | `自选作品/数据/商店.js`（零食 5 币上限 3 / 玩具 8 币上限 2），两分支不得修改 |
| 统一基准 | `自选作品/测试/基准商店.py`（静态统计 + JS 语义子集翻译 + 459 条穷举对拍） |
| 共同门槛 | `自选作品/测试/核对商店.py`（22 项契约检查） |
| 纪律 | 预期先于实现：基线空壳在基准上必然失败，两分支都必须让它转绿 |

## 二、两套方案

| | 方案 A `feature/plan-a` | 方案 B `feature/plan-b` |
|---|---|---|
| 分支提交 | `25c7c32` | 见 `git log feature/plan-b -1` |
| 思路 | **查表式**：线性查找商品 → 三段平铺 `if`（无此道具 / 已达上限 / 金币不足 / 正常购买） | **分派表式**：建索引 O(1) 取价 → `判定()` 归一结论 → `分派 = { "已购买": 执行购买 }`，拒绝分支共用一条返回 |
| 辅助函数 | `查道具()`（线性查找） | `建索引()`（预建 id→商品）、`判定()`（结论归一） |
| 预期（写在实现之前） | 代码最短、可读性一般 | "更优雅"，但多一层间接 |

> 标准里预先登记的**推测**是「A 可读性略差但代码最短，B 若用状态型写法可能出错」。
> 结果见第三节——**推测部分被验证，部分被推翻**。

## 三、实测数据（同一脚本、同一批 459 条用例）

| 指标 | 权重 | 方案 A | 方案 B | 胜出 |
|---|---|---|---|---|
| 正确性（459 条穷举对拍） | 40% | **459/459 = 100%** | **459/459 = 100%** | 平 |
| 不可变性 / 契约字段 / 六测试 | 门槛 | 全过 | 全过 | 平 |
| 净代码行 | 20% | **23** | 25 | **A** |
| 最大嵌套深度 | 20% | **3** | 4 | **A** |
| 圈复杂度（分支点+1） | 参考 | 10 | **8** | B |
| P95 耗时（Python 复刻 459 次调用） | 20% | **0.0241 ms** | 0.0262 ms | **A**（差异 < 10%，量级可忽略） |

**加权结论**：

- 正确性同为 100%，淘汰门槛无差异；
- 可读性（权重 20%）两项子指标（净行数、嵌套深度）**A 均胜**；
- 性能（权重 20%）A 略胜，但 0.024 vs 0.026 ms 的差距对"每次购买调一次"毫无影响，按标准属于**同分档**；
- 圈复杂度 B 更低（8 vs 10），但标准里它是**参考项**不是评分项——B 用一个分派表换掉了分支，分支点计数下降并不等于更好读。

**裁决：方案 A 胜出。**

> **诚实记录（推翻了标准里的推测）**：
> 标准第 4 节预测「B 若使用带状态的正则可能偶发错误」。实际实现 B 时**没有**用正则（用的是分派表），
> 所以那条风险假设**没有被验证到，属于预测落空**。两套实现在 459 条用例上都是 100% 正确，
> 真正的差异只在可读性与可维护性，而不在正确性上。

## 四、取舍决策

| 决策 | 内容 | 依据 |
|---|---|---|
| 合并 | `feature/plan-a` 合入 `main` | 标准 3.2 平票裁决顺序：正确性 → 可读性 → 性能，A 在可读性上明确胜出 |
| 废弃 | `feature/plan-b` **保留分支与文档，不删除** | 标准第 5 节纪律第 6 条：丢弃方案保留以便复核；也便于将来需要"分派表"结构时回看 |
| 未合并理由 | B 的分派表在商品只有 2 种、拒绝原因只有 3 种时属于**过度抽象**：多一层间接，换来的是"新增原因少改一行"。当前没有这个需求，属于第 8 周「画蛇添足」的典型诱因 | 课程第 8 周主题 |

## 五、合并前必须做的事（合并前逐项打勾）

- [ ] `feature/plan-a` rebase 到最新 `main`，确认 `merge-base` 仍是 `2d2b879` 之后的线性历史
- [ ] `git merge --no-ff feature/plan-a`，保留分支合并提交（历史图可读）
- [ ] 合并后重跑六测试 + `核对商店.py` + `基准商店.py`（应仍为 459/459）
- [ ] `git branch -d` **不执行**：B 分支保留
- [ ] README / PRD 无新增内容（本次只是把原本在 `养成.html` 里的硬编码下沉，尚未接入 UI）

## 六、本次实验暴露出的工程问题（可复用）

1. **"统一基准"本身就是最大工作量**：为了让两分支可比，必须先写一个能把 JS 语义子集翻译成 Python 的基准器
   （`基准商店.py` 约 700 行）。它踩到的坑全部记录在该文件注释里（`类` 变量遮蔽、对象字面量里的匿名函数、
   `i++`、`_取()` 读语义、`.length` 等）。**这是教学价值最高的一部分：评测基础设施比被测代码更难写。**
2. **两分支必须用同一份数据契约与同一个基准脚本**，否则"谁更好"无从谈起。
3. **标准先行**确实能防止事后找理由：本次 B 的圈复杂度更低，如果没有事先定权重，很容易被拿来说"B 更好"。

## 七、如何复现

```bash
# 1. 看两条分支
git log --oneline --graph --all -12
git diff 2d2b879 feature/plan-a -- 自选作品/养成商店.js
git diff 2d2b879 feature/plan-b -- 自选作品/养成商店.js

# 2. 分别跑基准（切分支后运行）
git switch feature/plan-a && python 自选作品/测试/基准商店.py --方案 a
git switch feature/plan-b && python 自选作品/测试/基准商店.py --方案 b

# 3. 对照标准打分
cat 作业/A3/A3-方案选型标准.md
```

> Windows 终端若报 `UnicodeEncodeError`，先 `set PYTHONUTF8=1`。
