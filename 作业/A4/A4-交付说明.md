## 二、评分点一：接口 Schema 约定（2 分）

### 2.1 改之前是什么样

字段契约**散落在测试脚本里硬编码**：

```python
# 核对数据.py 第 11 行
字段 = ["id", "名称", "人群", "卡路里", "碳水", "脂肪", "膳食纤维", "蛋白质", "食材", "步骤", "图片"]

# 核对动作.py 第 30-32 行
字段 = ["id", "名称", "部位", "器械", "目标肌群", "要点", "常见错误", "建议", "图片"]
部位允许 = {"上肢", "下肢", "核心", "全身"}
器械允许 = {"自重", "哑铃", "壶铃", "杠铃", "健身房器械"}
```

**四个问题**：

1. **契约不可见**：接手者要读三个测试脚本才能拼出数据结构
2. **契约与实现耦合**：改契约必须改测试代码，无法单独审阅
3. **覆盖不全**：装扮、家具、商店三份数据**完全没有契约检查**（只有零散的运行时逻辑）
4. **AI 代理无从遵守**：它不知道什么算「合法数据」，只能照抄现有条目

### 2.2 改之后：6 份声明式契约

| 文件 | 约束谁 | 关键约束 |
|---|---|---|
| `schema/食谱.schema.json` | 40 条食谱 | 11 字段顺序 / 卡路里 0–3000 / 小数位 ≤1 / 人群枚举 / 图片必须本地存在 |
| `schema/动作.schema.json` | 28 个动作 | 部位+器械枚举 / 要点 3–5 条 / **名称唯一** / 每部位至少 2 个 |
| `schema/装扮.schema.json` | 11 类 38 件 | **肤色全免费** / 图层禁含 `<script>` 与事件属性 / 色值仅肤色 |
| `schema/家具.schema.json` | 6 件 | 加成枚举 {0.05, 0.10} / 合计 0.35 / 上限 0.5 |
| `schema/商店.schema.json` | 2 件道具 | id 枚举 / 价格 ≥1 |
| `schema/存档.schema.json` | localStorage 4 键 + 两个结算函数的返回结构 | 字段顺序 / 结果枚举 / **不变量**（经验永不加成、断签不扣） |

**契约写法的特点**：不引入 JSON Schema 库（零依赖约束），而是约定了一个**极简命令式超集**：

```json
{
  "类型": "string",
  "格式": "^e\\d{3}$",
  "唯一": true,
  "非空": true,
  "本地路径": true,
  "禁止子串": ["<script", "onclick="],
  "枚举": ["上肢", "下肢", "核心", "全身"],
  "最少条数": 3,
  "最多条数": 5,
  "小数位最多": 1
}
```

### 2.3 校验器：`测试/校验schema.py`

按 schema 统一校验六类数据，输出：

```text
【食谱】按 schema/食谱.schema.json 校验
  ✓ 通过
【动作】按 schema/动作.schema.json 校验
  ✓ 通过
...
【通过】38 项检查全部符合 schema 契约
```

**设计取舍**：为什么不用 `jsonschema` 库？

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 用 `jsonschema` pip 包 | 标准、省事 | 破坏「零依赖」；换机器要 pip install | ❌ |
| 用 JSON Schema 标准格式手写校验器 | 标准格式 | 要自己实现 $ref/$defs 等，代码量翻倍 | ❌ |
| **自定义极简规则 + 自写校验器** | 零依赖、规则直观、中文可读 | 不是标准格式，外部工具不认 | ✅ 采用 |

> 这个取舍写进契约文件头注释，避免后人误以为「应该换成标准 JSON Schema」。

### 2.4 负向验证（证明校验器真的会拦）

| 故意改坏 | 期望 | 实际 |
|---|---|---|
| 商店价格 5 → 0 | 报「小于下限 1」 | ✅ 报错，exit=1 |
| 动作 e009 名称改成与 e024 重复 | 报「名称 存在重复值」 | ✅ 报错，exit=1 |

## 三、评分点二：AGENTS.md 规范（2 分）

### 3.1 为什么要有这个文件

课程第 7 周《巴别塔》的核心：**团队失败往往源于信息断层**。
本项目已有的 `交接说明.md` 是 v0.5 时期写给「下一个 AI」的，已经过时且没有约束力。

`AGENTS.md` 的定位是**控制面（Control Plane）**：不是介绍文档，而是「接手者的操作规范」。

### 3.2 结构（10 节）

| 节 | 内容 | 为什么需要 |
|---|---|---|
| 0 | 三句话：双击能跑 / 九项测试全绿 / 零依赖 | 30 秒建立心智模型 |
| 1 | 项目是什么、7 个页面 | 上下文 |
| 2 | 目录地图 + **三个产物文件不能手改** | 防止改生成物被覆盖 |
| 3 | **硬约束**：零依赖 / file:// / GLSL 只能 ASCII / 三不原则 / 分层约束 | **防止踩红线** |
| 4 | 五类改动的操作路径（加菜 / 加动作 / 改养成规则 / 改页面 / 改契约） | 直接可执行 |
| 5 | 九项验证命令 + 期望输出 | 怎么知道改对了 |
| 6 | 提交规范（类型前缀 + 四段式正文） | 历史一致性 |
| 7 | AI 协作纪律 | 课程要求 |
| 8 | 当前进度与已知待办 | 接手者知道下一步 |
| 9 | 遇到问题怎么办 | 排障顺序 |
| 10 | 5 分钟上手清单 | 可直接复制执行 |

### 3.3 最有价值的三条

根据第一次交接实测的反馈，这三点真正省了时间：

1. **「三个产物文件不要手改」**——`养成.html`、`数据/模型/*.js` 都是生成物，接手者若直接改会被下次生成覆盖
2. **「改了 JS 不改 Python 副本，测试仍然会绿」**——点破本项目最大的测试盲区
3. **目录地图 + 改动路径**——直接指出改哪里，不用翻代码

### 3.4 版本演进（重要）

`AGENTS.md` **不是一次写成的**，而是经过一轮真实交接使用后修订：

| 版本 | 提交 | 变化 |
|---|---|---|
| v1 | `6363423` | 初版 |
| v2 | `7cf9b14` | 按第 1 轮实测反馈修订 7 处（见第四节） |
| v3 | `8ef20a6` | 按第 2 轮反馈补「查重命中的处置」「测试盲区表」「id 乱序说明」 |
| v4 | `61a6132` | 按第 3 轮反馈：§4.2 重写为 7 步含同步条数、§5.1 口径冲突、新增 §9.1 常见失败表 |
| v5 | `a64bfed` | 按第 4 轮反馈：去掉自我失效的 id 举例、新增「当前分段」表与 7 处同步清单 |

**这正是课程要的「文档即系统、文档要经过使用验证」。**

## 四、评分点三：交接接手验证（2 分）

> 完整记录见 [`A4-交接实测记录.md`](A4-交接实测记录.md)，这里只给结论。

### 4.1 验证方法

起一个**全新的 AI 代理**（不读本对话、不看开发历史），只给它 `AGENTS.md` 和仓库，让它完成一个真实需求：

> 给动作库新增一条「卷腹（e029）」

**为什么用 AI 而不是同学**：课程原文要求「一个新的 AI 会话或新成员」；AI 是零先验的，且能留下完整的过程记录。

### 4.2 第 1 轮结果：完成任务，但暴露 7 个问题

| 指标 | 结果 |
|---|---|
| 是否完成任务 | ✅ 只改 1 个文件，未擅自动其他文件，未 commit |
| 耗时 | 12–15 分钟（**其中实际编辑只占 1 分钟**） |
| 自评 | 7/10 |

**抓到的真实缺陷**：

| # | 类别 | 问题 |
|---|---|---|
| 1 | 文档矛盾 | §4.2 只让跑 1 个测试，§5 要求 9 项全绿 |
| 2 | 文档矛盾 | §4.2 把配图写成必经步骤，与契约「图片允许为空」冲突 |
| 3 | 口径不一 | 测试数量：「六个」/「九条」/「八条」三种说法 |
| 4 | 路径错误 | §10 的 `start 自选作品\index.html` 在已 cd 后无效 |
| 5 | 语法错误 | §5 的 `set PYTHONUTF8=1` 是 cmd 语法，PowerShell 无效 |
| 6 | **契约漏洞** | 没有「名称唯一」约束 → 代理加出**第二条「卷腹」**，九项测试**全绿** |
| 7 | 术语混用 | 「7 页」与「6 页 + 养成页」混用 |

### 4.3 最关键的发现

> **代理完全按文档操作、按测试验证，产出了脏数据（两条同名动作），全程零告警。**

这说明：
- 测试全绿 ≠ 数据正确
- 契约的缺位会让「守规矩的执行者」也产出错误结果
- **交接文档必须经过真实使用验证，不能靠作者自检**

### 4.4 修复

| 修复项 | 提交 |
|---|---|
| `动作.schema.json` 的名称加 `"唯一": true` | `7cf9b14` |
| `AGENTS.md` 七处修订（加查重步骤、配图标可选、统一测试数量、修正 PowerShell 写法与路径、统一页码口径） | `7cf9b14` |
| 删除代理加出的重复「卷腹」，动作库回到 28 条唯一 | （未提交，恢复原状） |

### 4.5 第 2 轮结果：主动拦下错误需求，零改动

| 项 | 结果 |
|---|---|
| 是否执行 | **没有执行**——按修订后的「先查重」步骤发现库里已有同名动作，主动停手 |
| 改动文件 | **0 个** |
| 耗时 | 8–10 分钟 |
| 自评 | **8 / 10** |

代理的推理链：

> 插入 e029 → `核对动作.py` **会通过**（它只查 id 唯一和名称非空）
> → 但 `校验schema.py` **一定红**（名称唯一契约）
> → 数据会写进去，但提交门槛过不去，训练页还会出现两张重复卡片
> → **所以不写，把决策权交回人类**，并给出三条备选路

**两轮对比——这就是修订生效的证明：**

| 维度 | 第一轮（v1） | 第二轮（v2） |
|---|---|---|
| 发现重名的时机 | 事后（已加进去） | **事前（未落盘）** |
| 仓库结果 | 多一条脏数据，需回滚 | **零改动** |
| 依据 | 无（契约没有唯一性约束） | 文档「先查重」+ 契约 `"唯一": true` |
| 自评 | 7/10 | **8/10** |

> **一次修订（7 处文档 + 1 处契约）把「事后补救」变成了「事前拦截」。**
> 更深一层的结论：**软约束（文档提醒）必须配硬约束（契约拦截）**——
> 只写「先查重」时代理可能查了仍动手，加了 schema 唯一性后它才真的停手。

### 4.6 第二轮反馈 → v3 修订

| 它指出的问题 | 处理 |
|---|---|
| §4.2 没写查重命中后怎么办 | 新增步骤 1b：命中时停下、报告人类 |
| 没说明九项测试的重叠与盲区 | 新增 §5.1 对照表（`核对动作.py` 不查重名，`校验schema.py` 才查） |
| `动作.js` 的 id 是乱序的，「插在末尾」易插错 | §4.2 写明按注释段判断并列出实际顺序 |
| 数字前后不一（39 vs 40） | §5 加「数字别背，看结论」 |

### 4.7 第 3、4 轮：真实需求验证（证明修订没有过度收紧）

前两轮用的都是有缺陷的需求，只证明了「能拦错」。另跑两轮真实且不重复的需求：

## 六、本作业暴露的已知限制（诚实记录）

| 限制 | 说明 | 影响 |
|---|---|---|
| 契约格式非标准 | 自定义中文键名，外部工具（如 IDE 的 JSON Schema 插件）不认 | 换成标准格式需引入依赖，与零依赖冲突，暂不处理 |
| 所有测试硬编码 `D:\lab` | 换目录全废 | 已知隐患，记入待办（可改为相对路径推导） |
| 校验器是「我写它、它验我」 | 校验器本身无测试 | 用负向验证（故意改坏数据）代替 |
| 交接实测只有 AI，没有真人 | 同学没参与本作业 | A1 已有同学试用（罗文婷），本作业侧重「系统上下文」故用 AI |
| 第 2 轮实测可能仍有问题 | 文档修订无法保证一次到位 | 如实记录第 2 轮结果 |
