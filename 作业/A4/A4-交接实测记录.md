# A4 交接实测记录

> 课程第 7 周「盲人摸象交接实验」：让对方**只凭文档**接手，看卡在哪。
> 本记录完整保留两轮实测的过程、原始反馈与修订痕迹。

## 方法设计

| 项 | 设计 |
|---|---|
| 接手者 | 全新 AI 代理（**不读开发对话、不看 git 历史**，只有 `AGENTS.md` 和仓库文件） |
| 为什么用 AI | 课程原文要求「新的 AI 会话或新成员」；AI 零先验且能完整记录过程 |
| 任务 | 给动作库新增一条「卷腹（e029）」 |
| 任务为什么选「加数据」 | 这是最典型的「小改动、涉及多个约束」场景：字段契约、id 分配、图片可选性、部位分组排布 |
| 判定标准 | ① 能否只读 AGENTS.md 完成 ② 是否只改必要文件 ③ 是否跑通验证 ④ 是否踩坑 |

## 第一轮（对 `AGENTS.md` v1，提交 `6363423`）

### 执行结果

| 项 | 结果 |
|---|---|
| 完成任务 | ✅ 只改 `数据/动作.js`（+13 行），未改其他文件，未 commit |
| 耗时 | **12–15 分钟** |
| 其中实际编辑 | **约 1 分钟** |
| 自评 | **7 / 10** |

> 「真正省时间的部分是『三个产物文件不要手改』和『改了 JS 不改 Python 副本测试仍会绿』的盲区警告。」

### 关键发现：产出脏数据，九项测试全绿

代理严格按文档操作，添加了 `e029 卷腹`。但数据里**早已有 `e009 卷腹`**（核心 / 自重 / 腹直肌上部）。

结果：

```
数据/动作.js:193  "id": "e009", "名称": "卷腹", ...
数据/动作.js:256  "id": "e029", "名称": "卷腹", ...   ← 重复
```

**九项测试全部通过**——因为没有任何测试检查动作名唯一性。

代理自己发现了这个问题并主动上报：

> 「所有测试都不查重名，所以全绿——这正是『测试绿 ≠ 数据对』。按你的硬性要求我照文档加在了末尾（e029），但最终要么删掉 e009，要么把其中一条改成近义动作。请给指令。」

> **这条反馈的质量很高**：它既执行了指令，又识别出了指令本身的缺陷，还把决策权交回人类。

### 原始反馈：文档问题清单

代理给出的 6 条扣分理由（原文摘要）：

| # | 问题 | 原文节选 |
|---|---|---|
| 1 | §4.2 与 §5 冲突 | 「§4.2 只让跑 1 个测试，§5 要求 9 个全绿，新人必漏跑」 |
| 2 | 配图步骤矛盾 | 「§4.2 把『配图放 `<id>.jpg`』写成必经步骤，与契约『图片允许为空』冲突」 |
| 3 | 数量口径不一 | 「§0 说六个、§5 列九条、§10 写八条」 |
| 4 | 路径错误 | 「§10 的 `start 自选作品\index.html` 在此时已在 `自选作品/` 内，路径是错的」 |
| 5 | 语法错误 | 「§5 的 `set PYTHONUTF8=1` 是 cmd 语法，PowerShell 里跑不通」 |
| 6 | **契约漏洞** | 「没有名称唯一性检查，也没有提醒先搜一下是不是已经存在」 |

另有 3 条「文档没提但必须做」：

- `数据/动作.js` 解析限制（末尾 `];` 后不能有内容、不许尾逗号）
- 新动作的 id 该取「最大值 +1」还是「分区内顺延」，文档没说
- 文件头注释里复述了一遍字段契约，改 schema 时要同步

### 人类核实

逐条核实代理反馈，**全部成立**，但发现一处它没提到的：

> 我最初给出的交接任务本身就有问题——「新增卷腹」与已有数据重复。
> 这不全是文档的锅，**任务设计也要负一部分责任**。这条如实记在这里。

## 第二轮（对 `AGENTS.md` v2，提交 `7cf9b14`）

### 执行结果

| 项 | 结果 |
|---|---|
| 完成任务 | **没有执行**——判定需求与已有数据重复，主动停手 |
| 改动文件 | **0 个**（`git status` 干净，HEAD 仍是 `7cf9b14`） |
| 耗时 | 8–10 分钟 |
| 自评 | **8 / 10** |

### 决策过程（这是本轮最值钱的部分）

代理按修订后的 §4.2 **第 1 步「先查重」**，在 `数据/动作.js:192` 找到已有的 `e009 卷腹`：

| 字段 | 已有 e009 | 需求要求 | 判定 |
|---|---|---|---|
| 名称 | 卷腹 | 卷腹 | ❌ 冲突 |
| 部位 | 核心 | 核心 | 相同 |
| 器械 | 自重 | 自重 | 相同 |
| 目标肌群 | 腹直肌上部 | 腹直肌 | 上位关系，语义重合 |

它进一步推演了「硬做会怎样」：

> 如果插一条 e029 → `核对动作.py` **会通过**（只查 id 唯一和名称非空）→ 但 `校验schema.py` **一定红**（名称唯一契约）。
> 也就是说数据会写进去，但「九项全绿」这道门槛过不去，训练页还会出现两张重复卡片。

**它没有做任何修改，而是把决策权交回人类，并给出三条备选路：**

1. 判定为重复，关掉需求
2. 把需求理解为「完善现有 e009」（补要点、改肌群表述）——但明确指出「清空已有图片是倒退，不推荐」
3. 换名新增变式（如「仰卧卷腹」）——但需要人类给名字

> **这正是 A4 想要的能力**：不是「能动手」，而是「知道什么时候不该动手」。
> 第一轮的代理也会动手，但它同时执行了错误的指令；第二轮的代理**在动手前就拦住了**。

### 两轮对比：修订直接改变了行为

| 维度 | 第一轮（v1） | 第二轮（v2） |
|---|---|---|
| 是否发现重名 | 事后发现（已加进去） | **事前发现，未落盘** |
| 结果 | 仓库多一条脏数据，需人工回滚 | 仓库零改动 |
| 依据 | 无（契约里没有唯一性约束） | §4.2 步骤 1「先查重」+ schema `"唯一": true` |
| 自评 | 7/10 | **8/10** |
| 耗时 | 12–15 分钟（含回滚判断） | 8–10 分钟 |

**结论：一次修订（7 处文档 + 1 处契约）把「事后补救」变成了「事前拦截」。**

## 结论

### 两轮实测证明了什么

| 命题 | 证据 |
|---|---|
| 交接文档必须经过真实使用验证 | 第一轮暴露出 7 个作者自检发现不了的问题 |
| 一次修订能显著改变行为 | 同样有缺陷的任务，第二轮从「产出脏数据」变成「零改动拦截」 |
| 契约比文档更硬 | 文档写了「先查重」（软提醒），schema 写了 `"唯一": true`（硬拦截），第二轮代理**同时引用了两者** |
| 测试全绿 ≠ 数据正确 | 第一轮的重复动作在 `核对动作.py` 下完全绿灯 |
| 让代理汇报「卡在哪」比「做完了」更有价值 | 第一轮的价值几乎全在评估部分 |

## 可复用的经验

1. **交接验证必须用「真实的、没看过代码的人」**。作者自检发现不了「我以为写清楚了但其实没写」。
2. **最贵的错误是「守规矩也会错」**：第一轮代理完全照文档做、照测试验，仍然产出了脏数据。说明**文档与测试之间有缝隙**。
3. **好的接手者会拦住错误需求**。第二轮代理没有执行任务，而是识别出需求本身有缺陷——这比高效执行更有价值。
4. **反馈要逐条核实再采纳**。第一轮反馈 6 条全部成立，但「任务设计有缺陷」这条是我自己补的——如果只信代理的反馈，就会漏掉自己的责任。
5. **软约束（文档提醒）必须配硬约束（契约拦截）**。只有文档说「先查重」时，代理可能查了但仍动手；加了 schema 的唯一性后，它才会真的停手。
