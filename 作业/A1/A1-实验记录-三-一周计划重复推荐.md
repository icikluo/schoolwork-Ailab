# A1 实验记录（三）：一周计划重复推荐

> 对应 A1 第 3 评分项：**个人改动与解释（2 分）**
> 发现日期：2026-11-14 ｜ 来源：用户在 Chrome 中实际使用后反馈

---

## 一、发现过程

生成「增肌 · 每日 1200 kcal」的一周计划后，用户指出：**第 7 天与第 1 天排得一模一样。**

对照截图：

| | 早 | 午 | 晚 |
|---|---|---|---|
| 第 1 天 | 鸡胸肉卷饼 400 | 烤三文鱼 420 | 香蕉燕麦奶昔 350 |
| 第 7 天 | 鸡胸肉卷饼 400 | 烤三文鱼 420 | 香蕉燕麦奶昔 350 |

不只是首尾雷同，统计整个计划还发现：

```
3 次  水煮蛋配全麦吐司      ← 反复出现
2 次  鸡胸肉卷饼
2 次  烤三文鱼
...
1 次  藜麦鸡肉沙拉          ← 只用了一次
```

**有的菜用 3 次，有的菜只用 1 次。**

---

## 二、一个必须厘清的前提

「增肌」人群只有 **13 道菜**可选，一周最多排 **20 餐**。

13 < 20，所以在数学上**不可能完全不重复**。这一点必须在分析前说清楚，
否则会把"客观限制"误判成"程序缺陷"。

**真正的问题不是"有重复"，而是"重复得不均匀"。**

理想情况下 13 道菜排 20 餐，应该是 7 道菜各 2 次 + 6 道菜各 1 次。
实际却是 1 道菜 3 次、部分菜 1 次——分配失衡。

---

## 三、根因分析

原实现是一个三层候选筛选：

```javascript
// 第 1 层：本周完全没用过的菜
var 候选 = 食谱数据.filter(菜 =>
  菜.人群.includes(人群) &&
  已用ids.indexOf(菜.id) === -1 &&     // ← 关键：排除了本周用过的
  当日已用.indexOf(菜.id) === -1 &&
  菜.卡路里 <= 剩余额度
);

if (候选.length === 0) {
  // 第 2 层：本周菜用完了，允许跨天复用
  候选 = 食谱数据.filter(菜 =>
    菜.人群.includes(人群) &&
    当日已用.indexOf(菜.id) === -1 &&   // ← 只排除"今天"用过的
    菜.卡路里 <= 剩余额度
  );
}

候选.sort((a, b) => Math.abs(a.卡路里 - 餐预算) - Math.abs(b.卡路里 - 餐预算));
var 选中 = 候选[0];
```

**两个缺陷：**

### 缺陷 1：复用时不看「用过几次」

进入第 2 层后，排序只按卡路里接近度。卡路里 290 的「水煮蛋配全麦吐司」
在多个餐预算下都"刚好合适"，于是被反复选中。

### 缺陷 2：复用顺序固定

候选池顺序永远一样，第 2 层每次都从同一位置开挑。
第 1 天用掉的菜，到第 7 天重新变成"最近最少用"的候选，**于是复刻了第 1 天。**

---

## 四、修复

排序改为三级优先：

```javascript
候选.sort(function (a, b) {
  // 第一优先：本周用过次数少的
  var 次数a = 使用次数[a.id] || 0;
  var 次数b = 使用次数[b.id] || 0;
  if (次数a !== 次数b) return 次数a - 次数b;

  // 第二优先：距上次出现隔得越久越优先
  var 间隔a = 上次出现天[a.id] === undefined ? 99 : d - 上次出现天[a.id];
  var 间隔b = 上次出现天[b.id] === undefined ? 99 : d - 上次出现天[b.id];
  if (间隔a !== 间隔b) return 间隔b - 间隔a;

  // 第三优先：卡路里接近餐预算的
  return Math.abs(a.卡路里 - 餐预算) - Math.abs(b.卡路里 - 餐预算);
});
```

新增两个记录表：

- `使用次数[菜id]`：本周已出现几次
- `上次出现天[菜id]`：最近一次出现在第几天

**为什么要加「间隔」这一条**：只按次数排序时，第 7 天时所有菜都
"次数相同"，顺序又会退回固定排列，依然复刻第 1 天。
加上间隔优先级后，隔得越久的越优先，自然把重复拉开。

## 五、验证

### 修复前后的对比（增肌 13 道，排 20 餐）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单道菜最多出现 | **3 次** | **2 次** |
| 出现次数范围 | — | 1 ~ 2 次 |
| 完全没用到的菜 | 部分 | **0 道** |
| 第 7 天 = 第 1 天 | **是** | 否 |

### 全人群验证

| 人群 | 可选菜数 | 排餐数 | 最多重复 | 相邻两天全同 |
|---|---|---|---|---|
| 减脂 | 22 | 21 | 1 次 | 0 处 |
| 增肌 | 13 | 20 | 2 次 | 0 处 |
| 控糖 | 19 | 21 | 2 次 | 0 处 |
| 均衡 | 21 | 21 | 1 次 | 0 处 |

菜够用的减脂、均衡，**21 餐完全无重复**。

### 测试

`测试/逻辑复算.py` 从 81 项增至 **93 项**，新增 3 组断言：

- **10b** 每道菜都被用到；出现次数极差 ≤ 2
- **10c** 菜够用时完全无重复
- **10d** 相邻两天不完全相同（四个人群逐一验证）

## 六、这次修复说明了什么

### 测试全过仍然有 bug

修复前 81 项测试全部通过，其中也有"同一天内不重复"的断言。
但它测的是**同一天内**，从没测过**跨天重复**和**重复分布是否均衡**。

**测试只能证明它检查过的事情。**

### 「有重复」和「重复不均」是两回事

如果只看到"计划里有重复的菜"就下结论说程序有 bug，那是误判——
13 道菜排 20 餐必然重复。

必须先把**数学约束**算清楚，才能判断什么是真缺陷。

这一段判断过程，比修复本身更能体现工程思维。

### 用户视角才能发现的问题

这个 bug 是用户实际用了一遍才发现的，测试用例没想到，我也没想到。
和第 2 个实验（按钮被裁）一样：**交付质量最终由使用者的体验决定，不是由测试报告决定。**

      增肌 13 道排 20 餐时，个别菜出现 3 次、部分菜一次未出现。

      减脂/均衡 21 餐完全无重复；四人群相邻两天无雷同。
