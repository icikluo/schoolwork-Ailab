# A1 实验记录（四）：一周计划超额

> 对应 A1 第 3 评分项：**个人改动与解释（2 分）**
> 发现日期：2026-11-14 ｜ 来源：用户实际使用后反馈
> 前置：本文记录的问题，是修复实验三（重复推荐）时**引入的新缺陷**

---

## 一、发现过程

修复「一周计划重复推荐」后，用户在 Chrome 中重新生成计划，指出：

> 第 5 天 **1600 / 1200 kcal**，超目标值了

截图里第 5 天显示为红色（界面确实识别出了超额），
但**超额本身就不该发生**——红色只是提示，不是免责。

---

## 二、定位

看第 5 天排布：

| 餐次 | 菜品 | 卡路里 | 当时剩余额度 |
|---|---|---|---|
| 早 | 牛肉糙米饭 | 610 | 1200 |
| 午 | 香蕉燕麦奶昔 | 350 | 590 |
| 晚 | 红烧鸡腿配白米饭 | **640** | **240** |

晚餐时只剩 240 kcal，却排了一道 640 的菜。

**这一餐直接超了 400 kcal。**

---

## 三、根因：我上一轮修复引入的

修复「重复推荐」时，为了让每道菜都至少出现一次，加了两层「放宽」候选：

```javascript
// 第 2.5 层：宁可略超额度也不重复
if (候选.length === 0) {
  var 未用菜 = 食谱数据.filter(菜 =>
    菜.人群.includes(人群) &&
    已用ids.indexOf(菜.id) === -1 &&      // 只查"本周没用过"
    当日已用.indexOf(菜.id) === -1
    // ← 没有 菜.卡路里 <= 剩余额度 这一条
  );
  ...
  候选 = 未用菜;
}

// 第 3 层：完全放宽额度
if (候选.length === 0) {
  候选 = 食谱数据.filter(菜 =>
    菜.人群.includes(人群) &&
    当日已用.indexOf(菜.id) === -1
    // ← 同样没有卡路里上限
  );
}
```

**这两层把「不超额度」这个硬约束整个去掉了。**

### 这是一个优先级判断错误

当时我的想法是：「每道菜都应出现」和「不超额」都是好目标，冲突时让步一下。

**这个判断是错的。**

| 约束 | 性质 | 违反了会怎样 |
|---|---|---|
| 不超每日目标 | **硬约束** | 用户按计划吃就会超标，作品失去意义 |
| 每道菜都出现 | 软目标 | 只是不够丰富，不影响正确性 |

**硬约束不能被软目标兑换。** 这条不能讨价还价。

---

## 四、修复：重写为配额 + 上限 + 亏损补偿

不是打补丁，而是重写整个分配逻辑。

### 1. 三餐配额

```javascript
var 餐份量 = [0.35, 0.35, 0.3];   // 早 / 午 / 晚
var 餐配额 = 每日目标 * 餐份量[m];
```

早期用 30/40/30，但增肌人群没有小份菜（最低 260 kcal），
早餐配额 360 时午餐晚餐都排不出，导致部分天只有 2 餐。

### 2. 单餐硬上限（关键）

```javascript
var 后续餐数 = 每日餐次.length - m - 1;
var 单餐上限 = Math.min(
  每日目标 * 0.45,                     // 任何一餐不超过日额度 45%
  剩余额度 - 后续餐数 * 200            // 给后面每餐留出至少 200 kcal
);
```

**这一条直接堵死了「早餐吃 580 后午餐吃 590，晚餐排不出来」的情况。**

### 3. 亏损补偿

```javascript
var 前面欠的 = Math.max(前面配额和 - 当日已吃, 0);
var 目标卡 = Math.min(餐配额[m] + 前面欠的 * 0.6, 剩余额度);
```

早餐吃得轻，午餐会自动补上来，避免「每天只吃到 60%」。

### 4. 打分排序

```javascript
var 分 = 菜 => {
  var 卡差   = Math.abs(菜.卡路里 - 目标卡) / 每日目标;
  var 重复罚 = 使用次数[菜.id] * 0.20;
  var 间隔奖 = 距上次出现天数 * 0.05;
  return 卡差 + 重复罚 - 间隔奖;   // 分数越低越优先
};
```

**所有候选始终受 `菜.卡路里 <= 剩余额度` 约束，不再有例外分支。**

## 五、权重调参：有数据支撑的取舍

「吃够」和「不重复」是两个冲突目标，重复罚的权重直接决定取舍。

实测了 5 组权重：

| 重复罚权重 | 吃够率 | 不重复菜数 | 评价 |
|---|---|---|---|
| 0.30 | 79% ~ 88% | 8 ~ 17 道 | 吃不够 |
| 0.25 | 81% ~ 88% | 8 ~ 16 道 | 偏紧 |
| **0.20** | **84% ~ 90%** | **8 ~ 14 道** | **采用** |
| 0.15 | 84% ~ 93% | 8 ~ 13 道 | 重复偏多 |
| 0.10 | 90% ~ 96% | 8 ~ 9 道 | 重复太多 |

**选 0.20**：吃够率全部超过 84%，同时保留 8~14 道不重复的多样性。

这不是拍脑袋，是量出来的。

| 第 3 天 | — | 1360 / 1440（94%） |

| 第 7 天 | — | 1180 / 1440（82%） |

**7 天全部不超额，且都吃到了目标的 82% 以上。**

## 七、遗留问题：控糖数据不足

修复过程中发现一个**算法解决不了的问题**：

```
控糖 19 道菜，卡路里最高仅 340 kcal
三道菜合计最多 970 kcal
```

当每日目标设为 1600 以上时，**三道菜加起来就那么多，无论怎么排都吃不够**。

这必须说清楚：**这不是缺陷，是数据量限制。**

正确的判据不是「吃到目标的 70%」，而是「是否接近该群体菜品能达到的上限」。
所以测试里专门加了【10b-2】用「理论可达上限」作为分母，而不是用目标值。

要真正解决，需要补充高卡路里控糖菜（坚果、牛油果、全脂奶制品）。

## 八、这一轮修复的教训

### 1. 修复引入新缺陷是常态

| 轮次 | 动作 | 结果 |
|---|---|---|
| 第一轮 | 修复重复推荐 | **引入超额缺陷** |
| 第二轮 | 修复超额 | 重写算法，同时保住多样性 |

**第一次「修好了」，不代表真的好了。** 每次修复都要重新跑全部测试，
并且要**在本轮新增的测试里覆盖上一轮改动可能破坏的东西**。

### 2. 硬约束 vs 软目标

这次的核心教训是把两者混为一谈。
在写代码前就该明确：**哪些是可以让步的，哪些一步都不能让。**

对本作品而言：

| 级别 | 约束 |
|---|---|
| 🔴 绝不让步 | 不超每日目标、同一天不重复、只做 7 天 |
| 🟡 尽量满足 | 每条菜都出现、卡路里贴近配额、相邻天不雷同 |

### 3. 测试要覆盖「不变量」，而不只是「功能」

原来测的是「计划能生成出来、有 7 天」。
现在多了「**任何情况下都不超额**」这种不变量测试，
用 32 组参数组合穷举，而不是只测一个样例。


| | 实验一 | 实验二 | 实验三 | 实验四 |

| **类型** | 参数实验 | 布局缺陷 | 算法缺陷（多样性） | 算法缺陷（约束） |
| **发现方式** | 主动设计 | 自测清单第6项 | 用户使用 | 用户使用 |
| **现有测试能否发现** | 能 | 不能 | 不能 | 不能 |

四个实验构成一条完整的链条：
**主动实验 → 自测发现 → 使用发现 → 修复引入新问题 → 重写算法 → 建立不变量测试**。

这也是整份 A1 最想说明的一件事：
**交付质量不是"一次做对"，而是"每一轮都能发现并修好"的过程。**
