# A1 运行证据

> 作业 A1 第 1 评分项：**运行证据（2 分）**
> 作品：食谱搭配（`自选作品`）
> 版本：v0.1 ｜ 日期：2026-11-09

---

## 一、课程微实验原设计

课程标准第 1 周微实验：

> **运行崩溃实验**：在缺少全局依赖的干净虚拟机或新终端窗口中直接执行同伴拷贝的未封装脚本，
> 观察模块缺失或路径报错现象，体悟「在我的机器上能跑」不等于工程交付。

该实验的前提是**作品本身带有外部依赖**（如 Python 的第三方库）。

## 二、本作品的特殊情况

**食谱搭配是零依赖作品**：纯 HTML + CSS + JavaScript，双击 `index.html` 即可运行，
不安装 Node.js、不装任何第三方包、不连网络、不需要构建。

因此**无法复现「缺依赖崩溃」**——这本身是设计选择，不是缺陷。但它带来一个必须回答的问题：

> 既然不需要依赖，那这个作品是否也存在「只能在我电脑上跑」的风险？

**答案是：存在。** 只是风险来源不同。

## 三、替代实验设计

依赖换成了**文件与浏览器环境**。作品运行时依赖三样东西，缺一样就跑不起来：

| 依赖 | 作用 | 缺失后果 |
|---|---|---|
| `样式.css` | 全部视觉样式 | 页面变无样式白底黑字，布局塌陷（实测：**功能仍可用**） |
| `数据/食谱.js` | 提供 `window.食谱数据` | 启动自检触发，整页替换为「数据文件未加载」提示（实测） |
| `脚本.js` | 全部交互逻辑 | 外观看起来正常，但所有动态内容缺失、按钮无响应（实测静默失败） |

> 注：上表「缺失后果」一列已在实测后修正。原设计假设缺数据会抛 TypeError，
> 实测发现启动自检会先拦住，详见第三之二节。

于是把课程原微实验改编为：**在文件不完整的环境中运行作品，观察它如何失败。**

## 四、实验步骤（可直接照做）

### 准备

1. 复制整个 `自选作品` 文件夹到新位置，命名 `实验-缺文件`。
2. 用浏览器打开 `index.html`，**确认完整版能正常显示**（对照组）。
3. 关闭页面。

### 实验 A：缺少样式

1. 把 `样式.css` 改名为 `样式.css.bak`。
2. 打开 `index.html`。

**预期观察**：页面能打开，但**完全没有蓝色、没有卡片边框、没有排版**，
内容挤成一列黑字。功能可能仍可用，但**看起来根本不像一个作品**。

> 体悟：视觉资源也是交付的一部分。缺了它，功能完好但用户不敢用。

### 实验 B：缺少数据

1. 恢复 `样式.css`，把 `数据/食谱.js` 改名为 `食谱.js.bak`。
2. 打开 `index.html`，按 F12 打开开发者工具，切到 Console 面板。

**预期观察**（实验设计时的假设）：

- 「全部食谱」「为你推荐」「今日已记录」三个区域**全部空白**
- Console 中报错：`TypeError: Cannot read properties of undefined`

> 体悟：数据与逻辑拆开存放，一旦路径断裂，整个功能链断掉。

**实际观察（与本假设不符，原因见「三之二」节）**：

- 页面**没有**出现 TypeError 崩溃，也没有空白列表
- 整个页面被替换为一行红色中文提示：**「数据文件未加载，请确认 数据/食谱.js 存在。」**
- Console 中为资源加载失败：`Failed to load resource: net::ERR_FILE_NOT_FOUND`

### 实验 C：缺少逻辑

1. 恢复 `数据/食谱.js`，把 `脚本.js` 改名为 `脚本.js.bak`。
2. 打开 `index.html`。

**预期观察**（实验设计时的假设）：

- 页面保留**静态 HTML 外壳**（顶栏、卡片标题、空列表容器）
- 因为 `样式.css` 仍在，外观可能看起来「正常」
- 但**所有动态内容都是空的**，点「计算目标」**没有任何反应**
- 启动自检本身也在 `脚本.js` 里，所以**这次不会有中文提示**

> 体悟：如果确认表现为「看起来正常但完全无响应」，那这是最难查的一种失败——
> 页面好好的，用户以为是自己操作错了，而不是程序坏了。

**实际观察（与预期一致）**：

- 页面保留**完整静态外壳**：蓝色顶栏、白色卡片、圆角边框、阴影、按钮样式全部正常
- 五个功能区域均只剩 HTML 中写死的文案，**JS 生成的内容全部缺失**：
  - 「① 设置每日目标」：每日目标卡路里显示 `—`（HTML 初始占位符，从未被计算替换）
  - 「② 今日摄入」：五项营养均显示 `0` 而非 `0.0`（`toFixed(1)` 从未执行）
  - 「③ 为你推荐」：只剩「设置目标后开始推荐」
  - 「④ 食谱专区」：**五个分区按钮一个都没有**（全部/减脂/增肌/控糖/均衡全部缺失）
  - 「⑤ 一周食谱计划」：按钮在，但「固定 7 天」的说明文字缺失
- 点击「计算目标」**没有任何反应**
- 控制台**无报错**

### 关键判据：`0.0` 变成了 `0`

正常运行时，营养数值由 `toFixed(1)` 格式化，显示为 `0.0`。
实验中显示为 `0`，说明这段格式化代码**根本没有执行**——
这是「JS 未加载」在界面上的直接证据，比单纯看「列表是空的」更精确。

## 三之二、实验 B 结果与预期不符的原因

### 现象

按实验设计，缺数据应当出现 TypeError 崩溃；实测却是**一行明确的中文提示**。

### 原因

作品在 `脚本.js` 的 `初始化()` 开头包含一段启动自检（提交 `a4a152c`）：

```javascript
if (typeof window.食谱数据 === "undefined") {
  var 提示 = document.createElement("p");
  提示.style.cssText = "padding:48px 24px;text-align:center;font-size:16px;color:#d64545";
  提示.textContent = "数据文件未加载，请确认 数据/食谱.js 存在。";
  document.body.innerHTML = "";
  document.body.appendChild(提示);
  return;
}
```

检测到 `window.食谱数据` 未定义时，用明确文字替换整个页面并提前返回，
因此不会走到后续的渲染逻辑，也就不会抛 TypeError。

### 这段自检是怎么来的

它不是凭空加的。最初设计 A1 运行证据时，我判断「零依赖作品无法复现缺依赖崩溃」，
于是把实验改编为「缺文件」，并推测实验 C（缺 `脚本.js`）表现为静默失败。
基于这个判断，先加了自检作为改进。

**本次实测确认了这段自检确实生效。**

### 对比

| | 没有自检 | 有自检（实测） |
|---|---|---|
| 用户看到 | 空白页面，不知道哪里坏了 | 一行红字，直接说清缺哪个文件 |
| 排查方式 | 要开 F12 看报错 | 肉眼即可判断 |
| 修复动作 | 需猜测原因 | 提示直接给出修复方向 |

### 结论

预期与实测的差异**不是缺陷，而是改进生效的证据**。
这条差异已如实记录，未按原假设修改文档。

### 一个额外发现

实验 A 中，样式全部丢失后，**页面功能仍然完好**：

用户看到纯白底黑字的页面，第一反应是「这网站坏了」，尽管逻辑完全正常。

> 程序能跑通只是最低要求，能不能被人接受和使用是另一回事。

## 七、结论

### 发现了什么

1. 零依赖不等于零风险。作品的「依赖」从**软件包**变成了**文件结构 + 浏览器**。
2. **缺样式不会崩溃，但会让交付失败一半**（实验 A）——
   功能完好却让人以为程序坏了。
3. **自检能把「静默失败」转成「明确提示」**（实验 B）——
   同一处缺失，有无自检的用户体验差别很大。
4. **静默失败确实存在，且比报错更难发现**（实验 C）——
   页面看不出任何异常，但五个功能区全部失效，控制台也无报错。

### 三种失败模式的对比

| 缺失项 | 外观 | 功能 | 控制台 | 用户能否自行判断故障 |
|---|---|---|---|---|
| `样式.css` | 明显异常（白底黑字） | **正常** | 无错误 | 能，但会误以为网站坏了 |
| `数据/食谱.js` | 整页红色提示 | 不可用 | ERR_FILE_NOT_FOUND | 能，提示写明了原因 |
| `脚本.js` | **完全正常** | 全部失效 | **无错误** | **不能**——最容易误判为自己操作错误 |

三者中，**实验 C 的失败模式最隐蔽**：
页面没有任何视觉异常，按钮可点但毫无反应，控制台干净。
如果没有对照过正常版本，很难意识到是程序没加载。

### 原假设的验证情况

| 实验 | 设计时的假设 | 实测结果 | 是否印证 |
|---|---|---|---|
| A | 样式全丢，布局塌陷 | 一致；附加发现功能仍可用 | ✅ |
| B | TypeError 崩溃、列表全空 | **不符**，被启动自检拦住并给出中文提示 | ❌ 见三之二节 |
| C | 静默失败、难以排查 | 一致 | ✅ |

**实验 B 的预测错了**，文档已按实测记录，未按原假设改写。
实验 C 的静默失败特征则得到完整印证。

### 对作品的改进

启动自检已落地（提交 `a4a152c`），并在实验 B 中验证有效：

```javascript
if (typeof window.食谱数据 === "undefined") {
  var 提示 = document.createElement("p");
  提示.textContent = "数据文件未加载，请确认 数据/食谱.js 存在。";
  document.body.innerHTML = "";
  document.body.appendChild(提示);
  return;
}
```

但实验 C 暴露出这段自检的**局限**：自检代码本身就在 `脚本.js` 里，
当 `脚本.js` 整个缺失时，自检也随之消失，页面回到静默失败状态。

**后续改进方向**：把关键依赖检查移到 `index.html` 的内联脚本中，
使其不依赖于主脚本文件是否存在。
（列入后续版本，不在 v0.1 范围内）

### 与课程标准的对应

| 课程标准要求 | 本实验如何体现 |
|---|---|
| 「在我的机器上能跑」≠ 工程交付 | 同样是缺一样东西就跑不起来，只是缺的不是 pip 包 |
| 建立环境依赖与最小验收条件 | 明确了三样必需文件，并写进 README |
| 体悟交付的脆弱性 | 实验 A 证明「功能对」和「看起来对」是两回事 |
| 禁止期末补写虚假报告 | 12 项检查实做，实测结果与预期不符时如实记录并说明原因 |
