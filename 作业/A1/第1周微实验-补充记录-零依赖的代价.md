## 二、命题拆解：三个条件，本项目满足几个

把课程原命题拆成三个可检查的条件：

| # | 条件 | 本项目是否满足 | 说明 |
|---|---|---|---|
| ① | **未安装依赖**的环境 | ⚠️ 部分 | 作品零依赖，没有可"未安装"的东西；**但自动化测试需要 Python** |
| ② | 运行的是**同伴代码** | ❌ 不满足 | 两份记录跑的都是**自己的** `自选作品/`；同伴从未运行过本项目代码 |

**三个条件只满足半个。**

这不是执行疏漏，而是作品的**设计选择**导致的必然结果：

> 本项目在选题时就确定了「纯前端、零依赖、双击即开、断网可用」。
> 这个选择的收益是"换谁都能直接跑"，代价是——**"缺依赖崩溃"这件事在本项目上物理上不可能发生。**

## 三、同伴实测：三个人，全部没崩

### 3.1 实测事实

| 项目 | 内容 |
|---|---|
| 参与者 | 罗文婷（A1 同伴试用，见 [A1-同伴试用反馈表.md](A1-同伴试用反馈表.md)）+ 另外的同伴 |
| 结论 | **全部都能正常使用，无人遇到崩溃** |
| 结果 | 9 项任务独立完成 9/9，全程无需提示 |

### 3.2 这个"全绿"意味着什么

**它是本项目的成功指标，但它是本微实验的失败指标。**

| 视角 | "同伴全部能用"的含义 |
|---|---|
| 作为**作品质量**证据 | ✅ 优秀：可用性好，上手零成本 |
| 作为**本微实验**证据 | ❌ **无效**：没有任何崩溃可观察，实验组与对照组没有区别 |

课程这个实验的机理是：**崩溃 → 让学生看见环境依赖的代价 → 建立最小验收条件**。
当崩溃不发生，后半段（建立验收条件）就**失去了触发它的理由**。

## 四、深层原因：零依赖的代价是「从来没有被逼着写验收条件」

把两种情形并排放：

| | 有依赖的项目 | 本项目（零依赖） |
|---|---|---|
| 第一次交给同伴 | **必崩**：`ModuleNotFoundError` | **必不崩**：双击就开 |
| 崩溃后的自然反应 | 去写 `requirements.txt` | **什么也不会发生** |
| 验收条件的来源 | **被崩溃逼出来的** | **没有来源** |
| 风险 | 依赖声明缺失，但至少知道有这个问题 | **不知道自己缺这一块，因为没有东西提醒** |

**这正是《焦油坑》说的东西**：

> 单个程序能跑（Programming Product 的一半）→ 交给别人还能跑、还能改、还能继续，
> 才是 Programming **Systems** Product。中间那 9 倍的代价，不在"能不能跑"上，
> 而在"别人接手时要补多少没说出来的东西"上。

本项目"同伴全部能用"证明了**第一半**做得好。
但它**掩盖了第二半的缺口**——因为没有任何一次崩溃来提醒我"这里有东西没写下来"。

## 五、这个缺口的具体形态（已实测）

"没写下来"的东西，在项目里可以逐条点出来：

| # | 缺口 | 现状 | 实测依据 |
|---|---|---|---|
| 1 | **测试需要 Python，但没写版本要求** | [自选作品/README.md](../../自选作品/README.md) 写的是"装了 Python 3 的话"，没有版本号、没有"零第三方包"的明确声明 | 本次核对 README "跑测试"一节 |
| 2 | **作品端与测试端的依赖不是一回事** | 作品：零依赖（浏览器即可）；测试：需要 Python 3 + 标准库 | 见下方第六节实测 |
| 3 | **同伴的验证只覆盖"网页"，不覆盖"环境要求"** | 同伴全能用，指的是"网页能用"；而"需要什么环境"这件事，**跑成功的人也不会去问** | 3.1 节 + 第十节 |

第 3 条是本文件最重要的发现：

> **"同伴全部能用"，说的是网页能用；而微实验要测的"未安装依赖环境"，
> 问的是"运行它需要什么、你有没有写下来"。这两个问题在本次之前从未被分开过。**

补充（2026-11-24 核实）：同伴电脑**有 Python**，因此他确实具备跑测试的条件。
但这不改变第 3 条——**环境满足 ≠ 环境要求已写明**。
恰恰因为同伴环境满足，他永远不会有理由去问"这东西需要什么"，
于是**"没写"这件事可以无限期地不被发现**。

## 七、对照实验：什么样的项目才会真崩（外部参照）

为了让"本项目不崩"这件事可比较，本次另用一个**带第三方依赖**的脚本做了外部对照。
该脚本**不属于本仓库**，只用于说明崩溃长什么样：

| 场景 | 环境 | 实测输出 | 退出码 |
|---|---|---|---|
| 缺依赖 | 无第三方包的干净环境 | `ModuleNotFoundError: No module named 'pandas'` | **1** |
| 对照组 | 本机（已装 pandas） | 正常输出统计结果 | **0** |
| 注入式崩溃 | `sys.path` 置空 | `ModuleNotFoundError: No module named 'pkgutil'` | **1** |
| 换目录运行 | 从上级目录执行 | `FileNotFoundError: '学习记录.csv'` | **1** |

**这张表的意义：**它展示了"缺依赖崩溃"的真实形态——**退出码非 0、报错明确指出缺什么**。
把它和 6.2 节的结果并排看，就能看出本项目的处境：

| | 带依赖的项目 | 本项目 |
|---|---|---|
| 崩溃会不会发生 | 会，只要换个环境 | **不会，换个环境也一样** |
| 实验做不做得出来 | 做得出来 | **做不出来** |
| 该写的东西 | 依赖声明 | **本来是验收条件，但缺了也没人知道** |

## 八、结论与最小验收条件

### 8.1 结论

1. **课程原命题在本项目上不可复现**，原因不是执行失误，而是"零依赖"这一设计选择的直接后果。
2. **同伴"全部能用"是真的**，但它证明的是**作品可用性**，不能用作本微实验的证据。
3. **真正的风险不是"会崩"，而是"永远不会崩所以从来没检查过"**——本项目缺的不是依赖声明（那是完备的），而是**把环境要求写下来的习惯**。
4. 这与《焦油坑》的论断一致：**"能跑"与"能交接"之间的鸿沟，不会因为你恰好不需要踩坑就自动消失**——它只会在你没有防备的地方出现。本项目的体现是：**在补充本记录之前，同伴的验证只覆盖了"网页能不能用"，从未覆盖"环境要求写没写清"**；而这两件事，只有在把环境要求明确写下来之后才能被分开检查（见 8.2 节）。

### 8.2 落地的最小验收条件

针对第 8.1 节第 3 条，补一条验收条件（已写入 `自选作品/README.md`）：

> **任何"交给别人"的东西，必须写明它运行需要什么。**
> 本项目需要写明的只有两行：
> - 运行作品：任意现代浏览器（Chrome / Edge），**无需安装任何东西**
> - 运行测试：Python 3.8+，**无需安装任何第三方包**（仅用标准库）

**为什么这条之前没被发现缺：**

同伴电脑**有 Python**（已核实，见第十节），所以他无论是开网页还是跑测试都能成功——
**"能成功"这件事，本身就不会暴露"没写清楚"**。缺的从来不是一个能跑起来的环境，
而是**文档里那句"需要什么"**。这条验收条件的特殊性在于：它短到几乎不用写，但正因为它短，一直没写。

**交接结论：同伴已验证可用，且其环境满足本项目全部要求（Python 3.8+ / 现代浏览器）。**
