## 第 1 章 · 设计目标与红线

### 1.1 这是什么

给「食谱搭配」加一层**游戏化外壳**：把用户本来就在做的三件健康行为（吃饭 / 喝水 / 运动）
变成**可积累的经验值**，用经验值解锁**形象装扮**与**宠物**。核心是「健康行为 → 正反馈」的闭环。

### 1.2 三条设计红线（比功能更重要）

| 红线 | 为什么 | 具体怎么落 |
|---|---|---|
| **不鼓励节食** | **饮食类 App 最大的伦理风险**是激励机制诱人少吃。现有卡路里功能已有 1200 kcal 下限保护，养成系统绝不能把它挖穿。 | ① 三餐奖励**只看"是否打卡"**，不看吃少；② **吃撑/超标不扣经验**（见 4.5）；③ 奖励永不为负；④ 界面上不放任何"少吃→多经验"的暗示 |
| **不惩罚断签** | 断签惩罚会让人焦虑、然后干脆弃用。 | **连续天数只加不减**（见 4.3）；断签 = 归零重来，不扣任何已有经验 / 等级 / 物品 |
| **不改用户的健康行为本身** | 游戏是为了帮用户坚持，不是为了让他为了经验值瞎喝水、瞎运动。 | 喝水上限 8 次/日、运动上限 3 次/日（见 3.2）；不给"多喝水多经验"无穷收益 |

### 1.3 一句话验收（人肉可验证，不需要解释）

> 打开网页 → 点「记录」吃一道菜 → 侧栏经验条涨了 20 点、弹出「今日三餐 ×1」→
> 切到「养成」页 → 看到自己的形象和宠物 → 点「喝水」3 次，进度 3/8 →
> 攒够 100 经验后侧栏显示「升到 Lv.2」→ 去「商店」用金币买一件衣服穿上，形象立刻变了。

## 第 2 章 · 范围（做什么 / 不做什么）

### 2.1 本版做什么

1. **每日任务**：三餐、喝水、运动目标，达成给经验 + 金币。
2. **经验与等级**：累积经验 → 升级 → 解锁内容。
3. **金币**：经验之外的第二种货币，用于购买。
4. **形象**：发型 / 上衣 / 裤子 / 鞋子 / 配饰 五个部件，用户可自由换装。
5. **宠物**：领养一只，喂养 / 亲密度 / 升级；宠物的心情由**用户今天的达标情况**决定。
6. **商店**：用金币买衣服和家具。
7. **家具**：摆在"小窝"里（固定 6 个槽位），影响每日结算的金币加成。

### 2.2 本版**不**做什么（写死，防止范围爆炸）

| 不做 | 原因 |
|---|---|
| 好友 / 排行榜 / 串门 | 需要账号 + 服务器，违反纯前端零依赖。三不原则第 1 条 |
| 多只宠物 / 宠物对战 / 繁育 | 一只养好就够。多只 = 指数级的状态与 UI 复杂度 |
| 限定活动 / 限时掉落 / 抽卡 | 要处理时间窗口与概率，且**抽卡对健康 App 是坏设计** |
| 基础食材 / 烹饪小游戏（喂宠物要种菜） | 太重的第二套养成循环，会抢主线的注意力 |
| 宠物会死 / 会饿到掉级 | 惩罚机制，违反红线「不惩罚断签」 |
| 自定义形象（上传头像 / 捏脸滑块） | 画不出稳定效果，且需要图片存储。用**部件换装**代替 |
| 花哨图表（经验曲线图等） | 三不原则第 2 条，只做进度条 |
| 云端存档 / 多设备 | 三不原则第 1 条 |

## 第 3 章 · 数据模型（全部契约）

三个新存储键，全部带 `食谱搭配-` 前缀：

| 键名 | 值类型 | 说明 |
|---|---|---|
| `食谱搭配-养成存档` | object | 用户的等级 / 经验 / 金币 / 形象 / 宠物 / 已购物品（**唯一权威存档**） |
| `食谱搭配-养成每日` | object | 当天的任务进度，`{ 日期, 三餐, 喝水, 运动 }`，换天清零 |
| `食谱搭配-养成流水` | array | 经验获取记录，最近 30 条，用于「今日获得 N」与审计 |

### 3.1 养成存档 `食谱搭配-养成存档`

```js
{
  "版本": 1,                       // 存档版本号，未来迁移用
  "经验": 0,                       // 总经验（只增不减，整数 ≥ 0）
  "金币": 0,                       // 金币（整数 ≥ 0）
  "形象": {                        // 当前穿戴的部件 id
    "发型": "发-短发",
    "上衣": "衣-白T",
    "裤子": "裤-牛仔",
    "鞋": "鞋-帆布",
    "配饰": "饰-无"
  },
  "已购": ["发型:发-短发", "上衣:衣-白T", ...],  // 已拥有部件，格式 "<分类>:<id>"；默认免费部件也写进来
  "宠物": {                        // null 表示还没领养
    "种类": "猫",                  // 只能取 猫 / 狗 / 兔
    "名字": "小橘",                 // 1–8 个字符，用户可改
    "亲密度": 0,                   // 0–100
    "领养日": "2026-11-16",        // yyyy-MM-dd
    "上次喂食日": "2026-11-16"     // 用于判定今天喂没喂；无则 null
  },
  "家具": ["家具-木桌", null, null, null, null, null],  // 固定 6 个槽位，null = 空
  "今日获得经验": 0                // 冗余缓存，便于侧栏显示；可由流水重算
}
```

### 3.2 每日进度 `食谱搭配-养成每日`

```js
{
  "日期": "2026-11-16",   // 换天判定基准
  "三餐": ["早", "午", "晚"],  // 已完成打卡的餐次，去重、按 早→午→晚 顺序
  "喝水": 3,               // 0–8
  "运动": 1,               // 0–3
  "已喂宠物": false
}
```

**上限与去重规则（硬性）**

1. `三餐` 只能取 `"早" / "午" / "晚"`，**同一餐次只能计一次**（重复记录不重复给经验）。
2. `喝水` 计数上限 **8**，超过不加经验、也不报错，只提示「今天已经喝够了」。
3. `运动` 计数上限 **3**。
4. 换天：读到的 `日期` ≠ 今天 → 整个对象重置为今天的初始值，**不看老数据**。

### 3.3 来源判定 `生长来源`

每天的经验必须带来源，来源决定**奖励表**和**去重**：

| 来源字段 | 取值 | 触发时机 |
|---|---|---|
| 三餐 | `'早'` / `'午'` / `'晚'` | 在任意页面点「记录」成功，或计划页「标记已吃」成功 |
| 喝水 | `'喝水'` | 养成页点「喝水」 |
| 运动 | `'运动'` | 养成页点「运动打卡」 |
| 完成度 | `'达标'` | 三项任务全部达成时一次性给（见 4.6） |

## 第 4 章 · 规则引擎（核心，全部写成纯函数）

### 4.1 奖励表（唯一权威，写死）

```js
var 奖励表 = {
  早:   { 经验: 20, 金币: 5 },
  午:   { 经验: 20, 金币: 5 },
  晚:   { 经验: 20, 金币: 5 },
  喝水: { 经验: 5,  金币: 1 },   // 每次
  运动: { 经验: 30, 金币: 8 },   // 每次
  达标: { 经验: 50, 金币: 20 },  // 当日三项全部达成，一天一次
  喂食: { 经验: 0,  金币: 0 }    // 喂宠物不产经验，只加亲密度（见 4.9）
};
```

**为什么这么定**（写进 PRD，防止后人乱调）：一餐 20、三餐共 60；喝水 8 次满打满算 40；运动 3 次 90；
达标 50。三件全做完一天 ≈ **240 经验**。升满 Lv.10 需 4300 经验（见 4.2）→ **约 18 天**。
这是刻意的：**两周半就能看到满级**，让人有奔头，而不是一年都升不到三级。

**调整规则**：奖励表只能改数字，**不许改结构**（不许新增来源、不许让奖励为负）。

### 4.2 等级曲线

```js
// 升到下一级所需经验（从 Lv.n 到 Lv.n+1）
function 升级所需经验(等级) {
  if (等级 >= 10) return Infinity;       // 已满级
  return 100 + (等级 - 1) * 100;         // Lv1→2:100, Lv2→3:200 …… Lv9→10:900
}
```

从 0 经验起，升满 Lv.10 累计 `100+200+…+900 = 4500`？——**注意**：等级从 1 开始算，
Lv.1 本身不需要经验，所以累计 = 100+200+…+900 = **4500**。
再核对 4.1 的「一天 240」：4500 / 240 ≈ **19 天满级**。PRD 里写「约 19 天」。

```js
// 由总经验反推等级与当前级内进度（纯函数，核心）
function 由经验算等级(总经验) {
  // 返回 { 等级, 级内经验, 升级需要, 剩余, 是否满级 }
  // 等级 ∈ [1, 10]；满级时 级内经验 = 总经验 - 4500（可以为 0），升级需要 = 0，是否满级 = true
}
```

**用例（必须写进测试）**

| 总经验 | 等级 | 级内经验 | 升级需要 |
|---|---|---|---|
| 0 | 1 | 0 | 100 |
| 99 | 1 | 99 | 100 |

### 4.3 连续天数（连签）

```js
// 输入: 上次打卡日期(字符串或 null), 今天(字符串), 当前连续天数
function 更新连续天数(上次日期, 今天, 当前连续天数) {
  if (!上次日期) return 1;                    // 第一次
  if (上次日期 === 今天) return Math.max(当前连续天数, 1);  // 同一天，不变
  var 差 = 相差天数(上次日期, 今天);            // 纯整数，见下
  if (差 === 1) return 当前连续天数 + 1;        // 昨天 → +1
  if (差 <= 0)  return Math.max(当前连续天数, 1); // 时钟回拨等异常，不变
  return 1;                                    // 断了 → 从 1 重来（不扣任何东西）
}
```

`相差天数(a, b)` = `(按本地时间解析 b 的 0 点 - 按本地时间解析 a 的 0 点) / 86400000`，取整。
**必须按本地时区解析 `yyyy-MM-dd`**，不许用 `new Date("2026-11-16")`（那是 UTC，会差 8 小时）。

读写 `上次打卡日期` / `连续天数` 存到 `食谱搭配-养成存档` 的两个新字段：`上次打卡日`、`连续天数`。
**连续天数只增不减**（见 1.2 红线）。断签后显示为 1，不显示负数、不扣经验。

### 4.4 核心纯函数：打卡结算（整个系统的单点入口）

```js
/**
 * 打卡并结算。纯函数，不读写存储、不碰 DOM。
 * @param {object} 存档      - 养成存档（不改原对象，返回新对象）
 * @param {object} 每日      - 当日进度
 * @param {string} 来源      - '早'|'午'|'晚'|'喝水'|'运动'|'达标'
 * @param {object} 额外      - { 今日增量: {经验,金币}, 家具加成: 数字 } 便于测试注入
 * @returns {object} {
 *    存档: 新存档, 每日: 新每日,
 *    获得: { 经验, 金币 },        // 本次实际到账（可能为 0）
 *    结果: '已完成'|'已达标'|'已上限'|'无效来源',
 *    升了几级: 整数,
 *    是否刚达标: 布尔
 * }
 */
function 结算打卡(存档, 每日, 来源, 额外) { ... }
```

`结算打卡` 内部**严格按此顺序**执行（顺序不同结果不同，测试会对拍）：

```
① 校验来源合法 → 不合法直接返回 { 结果:'无效来源', 获得:{经验:0,金币:0} }，不动任何数据
② 去重/上限判定：
     · 三餐：来源已在 每日.三餐 里 → 结果='已完成'，获得 0
     · 喝水：每日.喝水 >= 8        → 结果='已上限'，获得 0
     · 运动：每日.运动 >= 3        → 结果='已上限'，获得 0
     · 达标：每日 已标记 达标 → 结果='已完成'，获得 0（标记存在 每日.达标 ✓ 新字段）
③ 记账：把来源计入每日（三餐 push、喝水+1、运动+1）
④ 查奖励表拿 {经验, 金币}；金币乘以 (1 + 家具加成)，经验不乘加成
⑤ 经验累加到 存档.经验；金币累加到 存档.金币
⑥ 连续天数：按 4.3 更新（只有 三餐/喝水/运动 触发，达标不触发）
⑦ 用 由经验算等级(旧经验) 与 由经验算等级(新经验) 对比，得出 升了几级
⑧ 达标检查：若 早/午/晚 三项都在 每日.三餐 里，且 每日.喝水 >= 目标、每日.运动 >= 目标（见 4.7），
   且 每日.达标 尚未标记 → 标记并**递归结算一次来源='达标'**（只递归一层，达标不触发连签）
⑨ 返回
```

**第④条的加成规则**：`金币 = Math.round(基础金币 × (1 + 家具加成))`，`家具加成` 上限 0.5。
经验**永不加成**（经验只由真实行为产生，防止"摆家具刷级"）。

### 4.5 三条反节食规则（必须显式实现 + 显式测试）

1. **吃撑不扣经验**：`结算打卡` 永远返回 `获得.经验 >= 0`。**全系统不存在任何负奖励分支**。
   测试要断言：对任意输入，`获得.经验 >= 0 && 获得.金币 >= 0`。
2. **记录越少不会越多**：经验只按「餐次是否打卡」计，**完全无视当餐卡路里值**。
   测试要断言：同样打卡三次，吃 3000 kcal 的一天与吃 1500 kcal 的一天**经验完全相同**。
3. **喝水/运动不鼓励过度**：上限封顶（4.2 已有），且**重复打卡没经验**（4.4 步骤②）。

### 4.6 达标判定

```js
var 每日目标 = { 三餐: 3, 喝水: 8, 运动: 1 };   // 运动默认目标 1 次（不是 3 次），避免逼人天天练
function 每日是否达标(每日, 目标) {
  return 每日.三餐.length >= 3 && 每日.喝水 >= 目标.喝水 && 每日.运动 >= 目标.运动;
}
```

达标 = 一次性奖励 50 经验 + 20 金币，**一天最多一次**（`每日.达标` 标记）。

### 4.7 宠物的心情与状态（不惩罚，只反映）

```js
/**
 * 由今日状态推导宠物心情。纯函数。
 * 返回 { 心情: '开心'|'一般'|'饿了', 亲密度: 数字 }
 */
function 宠物心情(每日, 存档) {
  // ① 今天喂过食 → 亲密度 +5（不超过 100）；没喂 → 不加（不扣）
  // ② 心情三级：
  //    每日三项全部达成（不论喝水量） → '开心'
  //    三项完成 ≥ 1 项            → '一般'
  //    一项都没做                 → '饿了'
  // ③ 亲密度只增不减（红线：不惩罚）
}
```

喂宠物（`喂食`）：一天一次，`每日.已喂宠物 = true`，亲密度 +5。
**喂食不消耗任何资源**（不做"喂食要花金币"——那会制造焦虑型经济）。

### 4.8 宠物升级（亲密度里程碑，不设等级条）

亲密度每 10 点 = 1 颗心，最多 10 颗心（100 满）。满心后宠物外观变化（见第 9 章）：
- 0–29：普通
- 30–69：长大一点（CSS 放大 1.1 倍 + 加配件阴影）
- 70–100：戴上皇冠

### 4.9 领养宠物

- 首次进入养成页且 `存档.宠物 === null` → 显示领养弹窗：选种类（猫 / 狗 / 兔）+ 起名。
- 名字规则：去首尾空格后 **1–8 个字符**，禁止为空；允许中文、字母、数字。
  非法时按钮禁用并给红字提示，不弹 alert。
- 领养后 `宠物 = { 种类, 名字, 亲密度: 0, 领养日: 今天, 上次喂食日: null }`。
- **不可更换种类**（避免反复领养刷亲密度）；名字可改（按钮「改名字」，同套校验）。

### 4.10 家具加成

小窝 6 个槽位，每件家具给一个加成：

| 家具 | 家具加成 |
|---|---|
| 家具-木桌 | 0.05 |
| 家具-绿植 | 0.05 |

## 第 5 章 · 经验在既有功能里怎么"长出来"

养成系统**不新开一套记录入口**，而是**寄生在现有行为上**——用户什么都不用多学。

### 5.1 挂载点（必须精确接到这里）

**只有一个真正的挂载点：`脚本.js` 的 `添加记录(菜, 指定餐次, 份量)`（约 955 行）。**

**为什么只有一个**：读代码后可确认——计划页的 `标记计划已吃(天序号, 餐)`（约 858 行）
**内部就是调用 `添加记录(菜, 餐.餐次)`**（863 行），`餐` 只有 `id` / `餐次` / `卡路里`，**没有 `名称`**。
所以：

- 只改 `添加记录` 一处，计划页「标记已吃」**自动继承**养成打卡，不需要也不允许另改一处
  （两处都接会**同一餐算两次经验**，这是最容易犯的错）。
- `加餐`（`判定餐次()` 在 21 点后返回 `补记餐次` 的结果）**不计入三餐**：加餐不算「一日三餐」，
  避免用户为攒经验乱记加餐。加餐不打卡、不给经验，也不提示。

**`添加记录` 的改法**（在 `写记录(记录);` 之后、`刷新所有();` 之前插入）：

```js
    // v0.6：饮食记录 → 养成经验。养成出任何错都绝不能影响记录本身。
    try {
      if (window.养成系统) window.养成系统.打卡(营养.餐次);
    } catch (e) { console.warn("养成打卡失败", e); }
```

> 实现者注意：`添加记录` 里**没有**名为 `餐次` 的变量。餐次是写在记录条目上的：
> `餐次: 指定餐次 || 判定餐次()`。请按实际代码改成 `记录[记录.length - 1].餐次`，
> 或先把餐次提成一个局部变量 `var 本条餐次 = 指定餐次 || 判定餐次();` 再复用。
> **以实际代码为准，不要照抄本文件的变量名。**

### 5.1.1 其余两个来源（养成页自己的按钮）

| 来源 | 位置 | 触发 |
|---|---|---|
| 喝水 | `养成.html` 的「💧 喝水 +1」 | `window.养成系统.打卡("喝水")` |
| 运动 | `养成.html` 的「🏃 运动打卡」 | `window.养成系统.打卡("运动")` |

### 5.2 关键要求

1. 挂载必须**包一层 `try/catch`**。养成系统出任何错，**绝不能让记录失败**——记录是主线，养成是附加。
   ```js
   try { window.养成系统.打卡(餐次); } catch (e) { console.warn("养成打卡失败", e); }
   ```
2. 餐次取值直接复用现有 `判定餐次()` 的结果；只接受 `'早'/'午'/'晚'` 三个值。
3. 半份 / 整份**不影响经验**（固定 20 点）。
4. **重复记录同一餐**：用户可能在总览记了午饭，又在计划页「标记已吃」一次。
   去重由 `结算打卡` 步骤②负责（`每日.三餐` 已有该餐次 → 获得 0），挂载点不做任何判断。

### 5.2 侧栏常驻经验条（6 页都要有）

现有每页侧栏已有 `侧栏目标 / 侧栏今日` 区块。在其下方新增：

```html
<div class="侧栏养成">
  <div class="养成行">
    <span class="养成等级" id="侧栏等级">Lv.1</span>
    <span class="养成经验值" id="侧栏经验文字">0 / 100</span>
  </div>
  <div class="进度条 养成条" role="progressbar" aria-valuemin="0" aria-valuemax="100">
    <div class="进度填充" id="侧栏经验填充"></div>
  </div>
  <div class="养成金币"><span id="侧栏金币">0</span> 金币</div>
</div>
```

要求：

- **6 个 HTML 全部加**（顺序、位置一致，都在「侧栏今日」之后、「侧栏导航」之前）。
- `检查契约.py` 会校验 id，所以 id 命名必须与 JS 一致。
- 满级时：等级显示 `Lv.10 满级`，经验条填满 100%，文字改为「已满级」。
- 侧栏高度有限，养成块必须**紧凑**（≤ 70px），不能把导航挤出屏幕。
- `≤900px` 侧栏转顶部导航时，养成块**隐藏**（顶部空间不够），但信息可在养成页看。

### 5.3 经验增长的可见反馈（必须有，否则用户感知不到）

点「记录」后：

1. 侧栏经验条**有动画**（宽度过渡 0.3s），血量涨的感觉。
2. 冒出一个**浮层提示**（toast，页面右下角，2 秒后淡出）：
   - 普通：`+20 经验 · +5 金币`
   - 升级：`升级！Lv.2`（并播放一个 CSS 缩放动画）
   - 上限：`今天的喝水已经记满啦`（灰色，不是红色）
3. **不许用 `alert()` / `confirm()`**（现有代码风格也没用）。全部用 DOM 浮层。

## 第 9 章 · 数据契约（`数据/装扮.js` / `数据/家具.js`）

### 9.1 装扮字段契约

> 写法必须与 `数据/动作.js` 一致：带引号的 JSON 风格键。

```js
window.装扮数据 = {
  "发型": [
    { "id": "发-短发", "名称": "短发", "价格": 0, "等级要求": 1, "图层": "<path d=\"...\"/>" },
    ...
  ],
  "上衣": [],
  "裤子": [],
  "鞋":   [],
  "配饰": []
};
```

**每个分类的"第一个部件"是默认穿戴**，其 `价格` 必须为 0。

| 字段 | 类型 | 规则 |
|---|---|---|
| id | 字符串 | 唯一，格式 `发-xxx` / `衣-xxx` / `裤-xxx` / `鞋-xxx` / `饰-xxx`，**分类前缀与所在分类必须对应** |
| 名称 | 字符串 | 非空，≤ 6 字 |
| 价格 | 整数 | ≥ 0；**0 表示默认免费拥有** |
| 等级要求 | 整数 | 1–10；买入时等级需 ≥ 此值 |
| 图层 | 字符串 | 一段合法 SVG 片段（`<path>` / `<circle>` / `<rect>` / `<g>`），**必须是常量**，不含 `<script>`、不含事件属性、不含外链 |

**数量要求（写进测试）**

| 分类 | 总数 | 免费（价格 0） | 价格区间 |
|---|---|---|---|
| 发型 | ≥ 8 | ≥ 2 | 20–120 |
| 上衣 | ≥ 10 | ≥ 2 | 30–150 |
| 裤子 | ≥ 8 | ≥ 2 | 30–120 |
| 鞋 | ≥ 6 | ≥ 2 | 20–100 |
| 配饰 | ≥ 6 | ≥ 1 | 40–180（含一个 `饰-无`，价格 0） |
| **家具** | **6**（固定） | 0 | 80–300 |

**免费部件放最前**：默认穿戴 = 每个分类的**第一个免费部件**。

### 9.2 家具字段契约

```js
window.家具数据 = [
  { "id": "家具-木桌", "名称": "木桌", "价格": 80, "加成": 0.05, "图层": "<g>...</g>" },
  ...
];
```

- `id` 格式 `家具-xxx`，6 件，id 互不相同。
- `加成` ∈ {0.05, 0.10}，合计 0.35（≤ 上限 0.5）。
- 家具用**小图标画法**（`viewBox="0 0 100 100"`），不必写实。

### 9.3 宠物 SVG

宠物不在数据文件里逐条列，而写在 `养成.js` 里的常量对象：

## 第 11 章 · 挂载与集成细节（最容易写错的地方，照抄）

### 11.1 加载顺序

每个 HTML 的 `<body>` 末尾，**在 `脚本.js` 之前**加载数据与养成模块：

```html
<script src="数据/食谱.js"></script>
<script src="数据/动作.js"></script>
<script src="数据/装扮.js"></script>
<script src="数据/家具.js"></script>
<script src="养成.js"></script>
<script src="脚本.js"></script>
```

**为什么养成.js 在 脚本.js 之前**：脚本.js 的 `初始化()` 里要调用养成系统的重绘；
且养成.js 需要在 `DOMContentLoaded` 之前把 `window.养成系统` 挂好。两者都监听 `DOMContentLoaded`，
绑定顺序决定执行顺序——**养成先注册，脚本后注册**。

### 11.2 `脚本.js` 的改动（**只有一处**，约 4 行）

只改 `添加记录()`（约 955 行），在 `写记录(记录)` 之后加：

```js
    // v0.6：饮食记录 → 养成经验。失败绝不能影响记录本身。
    try {
      if (window.养成系统) window.养成系统.打卡(营养.餐次);
    } catch (e) { console.warn("养成打卡失败", e); }
```

**`标记计划已吃()` 不要改**——它内部调用 `添加记录`，会自动继承（见 5.1）。
在它里面再接一次会导致**同一餐算两次经验**。

**注意**：先读这两个函数的实际代码确认变量名（`添加记录` 里没有 `餐次` 变量，
餐次写在记录条目上，见 5.1 的提示），按实际结构写，不要照抄本文件的变量名。

### 11.2.1 既有项目的三个写法惯例（照抄，别自创）

## 第 14 章 · 为什么这样设计（给评审看的取舍说明）

1. **为什么经验只看"打没打卡"，不看卡路里？**
   因为一旦卡路里参与奖励，用户就会为了升级少吃。这是健康类产品最常见的坑，且与项目已有的
   1200 kcal 下限保护自相矛盾。打卡制简单、公平、可解释。

2. **为什么只加一只宠物、不支持多只？**
   每多一只宠物，状态（亲密度/喂食/心情/外观）都要翻倍，UI 也要重做。一只养好足够提供情感联结。

3. **为什么商店不做独立页，塞进换装抽屉？**
   导航已经有 6 项，第 7 项「养成」已到密度上限。且「买 → 穿」是一个连续动作，分开要来回跳页。

4. **为什么宠物不会掉级、不会死？**
   惩罚机制在养成系统里性价比极低：用户断签时本来就容易弃用，再加惩罚会加速流失。

5. **为什么先写纯函数再写 UI？**
   项目没有 Node.js，只能靠 Python 对拍测逻辑。把规则和渲染彻底分离，是这个小项目唯一能
   做到「可自动化验证」的方式。

6. **为什么经验条要放侧栏而不是只在养成页？**
   用户的打卡动作发生在**记录/食谱/计划页**，反馈必须发生在**动作发生的地方**。
   把反馈藏在另一个页面里，等于没有反馈。
