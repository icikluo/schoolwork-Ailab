## 0. 结论摘要

1. **原稿骨架是对的，可以直接用**：纯函数分离、奖励只看打卡不看卡路里、不惩罚断签、先规则后 UI、Python 对拍——这几条判断都对，而且和这个项目的工程纪律吻合。不需要推翻重来。
2. **但有 8 处会真实翻车的地方必须改**（第 2 章），其中 2 处是"用户正常操作就吃亏"的 bug，1 处是"5 分钟刷满一天"的漏洞，1 处是最大的落地风险（SVG 拼装）。
3. **数值要重算**：原稿 19 天满级 vs 60 天买齐，节奏是错位的；达标线=上限（喝水 8/8）会让"达标"变成"打满"。
4. **手机端会失去全部反馈**：原稿在 ≤900px 直接隐藏经验条，而手机是最可能的使用场景。
5. **3D：能做，按用户定稿做成「人物 2D + 房间 3D」混合渲染**。房间用浏览器原生 WebGL1 手写约 200 行渲染器（零依赖、`file://` 可跑、程序化几何不需美术资产），人物用内联 SVG 分层叠加在 canvas 上（DOM overlay）。场景数据与规则层解耦，3D 做不动也能降级成 2.5D，玩法不受影响。详见第 5 章。
6. **捏脸是"预设选择器"**：脸型 / 肤色 / 眉 / 眼 / 嘴 / 腮红 / 发型等从网页给的选项里挑，不做上传与滑块；单存档、不做多档位。首版 34 件部件 + 4 个肤色。

## 2. 必须改的 8 处（问题 → 改法 → 理由）

### R1 22 点后吃晚饭，永远拿不到"晚"的经验（bug）

**问题**：`判定餐次()` 是 `<21` 才返回"晚"，21 点后返回"加餐"；而原稿规定"加餐不计三餐"。结果是**晚睡的人只要 21 点后记录晚餐，就永远不可能达标**，且当天少 20 经验。这不是边界情况，是常见作息。

**改法**：养成侧不看"加餐"这个标签，做一次兜底：
- 来源为"加餐"且 `每日.三餐` 里还没有"晚" → **记为"晚"**（当天仅一次）；
- 来源为"加餐"且"晚"已记 → 忽略，不给经验、不提示。

**理由**：21 点后那一餐，用户语义上就是晚饭。兜底一次即可，不会变成无限刷。

### R2 计划页"标记已吃"可以让三餐在 5 分钟内刷满（漏洞）

**问题**：`标记计划已吃()` 会把 `餐.餐次` 直接传给 `添加记录`，餐次来自计划本身，**与当前时间无关**。早上 8 点就能把计划里的"晚餐"标成已吃，于是 8:03 就能凑满三餐 + 达标 ≈ 240 经验。演示时被问到会很尴尬。

**改法**：挂载点带一个"是否强制餐次"标记，并加**餐次时间窗**：
- 强制餐次（计划页）且在窗口内 → 正常计经验；不在窗口内 → 记录照写，但 `结果='未到餐点'`、获得 0；
- 非强制（记录页/总览页，餐次由当前时间自动判定）→ 不校验窗口。

| 餐次 | 时间窗 |
|---|---|
| 早 | 04:00–09:59 |
| 午 | 10:00–14:59 |
| 晚 | 15:00–03:59（跨零点，指"今天这一顿晚饭"） |

**理由**：允许提前一点（15:00 记晚饭是正常的），但不允许把一天压缩成 5 分钟。

### R3 达标线 = 上限，等于没有达标线

**问题**：原稿"达标"要求喝水 8 杯，而喝水上限也是 8 杯。也就是说必须**打满**才算达标，实际大部分人拿不到那 50 经验，`是否刚达标` 长期为 false，达标徽章变成摆设。

**改法**：**达标线低于上限**——`每日目标 = { 三餐: 3, 喝水: 6, 运动: 1 }`，上限仍是 8 / 3（多喝多练仍有经验，但不再影响达标）。

**理由**：目标要留余量，这是行为设计常识；6 杯（约 1.5L）也是更现实的日常量。

### R4 经济节奏错位：19 天满级，60 天才买齐

**问题**：原稿算下来一天满额 67 金币，全部装扮 + 家具约 4000+ 金币 → 约 60 天。结果：**19 天满级后进入"什么目标都没有"的空窗期**，收集曲线比等级曲线慢 3 倍。

**改法**（两条一起做）：

1. **重定价**，把总价压到约 2200–2400：

| 分类 | 扩量后数量 | 免费 | 价格区间 |
|---|---|---|---|
| 脸型 / 眉 / 眼 / 嘴 / 腮红 | 15 | 6 | **10–40**（五官便宜，先让人捏得起来） |
| 肤色 | 4 | 4 | 0（全部免费，肤色不该收费） |
| 发型 | 8 | 2 | 20–60 |
| 上衣 | 10 | 2 | 30–80 |
| 裤子 | 8 | 2 | 25–60 |
| 鞋 | 6 | 2 | 15–50 |
| 配饰 | 6 | 2（含 `饰-无`） | 40–90 |
| 家具 | 6 | 0 | 60–150 |

约束：**任何单件 ≤ 3 天收入（≈200 金币）**，不能出现"看着买不起"的货；**肤色 4 档全免费**（收费会让人对"自己的样子"产生付费焦虑，与红线冲突）。v3 新增的五官部件定价压低，总价仍控制在约 2300。

2. **满级后接星星**：`Lv.10` 之后经验继续累积，每 500 经验 +1 星（显示 `Lv.10 ★3`），不新增任何系统。

**理由**：让**满级（约 19–25 天）早于买齐（约 30–35 天）**，满级后仍有"差两件没凑齐"的牵引，而不是满级即弃。

### R5 手机上没有任何经验反馈

**问题**：原稿写"≤900px 侧栏转顶部导航时，养成块隐藏"。但记录动作在手机上同样发生，**反馈被藏起来的反馈等于没有反馈**——这恰好违反原稿自己在第 14 章写的第 6 条理由。

**改法**：≤900px 时，把养成块压缩成**顶栏右侧胶囊**：`Lv.3 · 320/500 · 42` （等级 · 经验 · 金币），点击进养成页；进度用胶囊底部的 2px 细条表示。

**理由**：占位极小，但"涨了"看得见。

### R6 存档只有一份，且不可迁移（最大的用户损失风险）

**问题**：全部资产在 `localStorage`，一次"清除浏览数据"或者换电脑，形象、宠物、连续天数全没。养成系统与普通数据不同——**用户对宠物和形象有情感投入，丢了就是差评**。原稿完全没处理。

**改法**（成本很低）：
- 养成页底部加「存档」：**导出**（把 `食谱搭配-养成*` 四个键序列化成一段文本放进 `<textarea>`，用户自己复制走）+ **导入**（粘贴文本 → 校验版本与字段 → 覆盖）。不写文件、不联网、不弹窗。
- 导入必须**先校验再写**：结构不对就整段拒绝并提示，绝不半覆盖。

**理由**：纯前端做不到云同步，但"用户可以自己备份"能挡住 90% 的丢失场景，也顺便给了"换设备"一个说法。

### R7 冗余字段会漂移

**问题**：`今日获得经验` 是缓存字段。一旦某次写入失败或跨标签并发，它就和流水对不上，最后没人知道哪个是真的。

**改法**：删掉该字段，`今日获得` 一律**从流水按日期求和**（流水只留 30 条、每天最多 15 条，够用）。

**理由**：同一个事实只存一处。

### R8 SVG 拼装没有坐标契约（最大的落地风险）

**问题**：原稿要求"每个部件一层 `<g>`，按当前形象拼进 `viewBox 0 0 200 320`"，但**没有规定任何锚点/坐标带**。实际施工时，衣服必然对不上身体——手写的 38 个部件 × 5 层叠加，靠肉眼一件件调到对齐，是最容易做到崩溃的一步，而且改一件要重调全部。

**改法**（三条）：

1. **写死坐标带**（所有部件都在同一画布绝对定位，不用 `transform`）：

| 部位 | 坐标带（y） | 锚点 |
|---|---|---|
| 脸 / 五官 | 34–108 | 脸心 (100, 70)；详见 5.6 脸部坐标带 |
| 头发 / 头饰 | 24–112 | 头顶 y=30，头心 y=68 |
| 上衣 | 108–212 | 肩线 y=120，下摆 y=208 |
| 裤子 | 196–292 | 腰线 y=204 |
| 鞋 | 278–314 | 脚底线 y=312 |
| 配饰 | 96–140（项链）/ 24–70（帽子） | 颈点 y=100 |

   图层顺序固定：`身体 → 裤子 → 鞋 → 上衣 → 脸(带肤色) → 眉 → 眼 → 腮红 → 嘴 → 头发 → 配饰`。

2. **首版减量**：脸型 3 / 肤色 4 / 眉 3 / 眼 4 / 嘴 3 / 腮红 2 / 发型 4 / 上衣 5 / 裤子 4 / 鞋 3 / 配饰 3 = **34 件部件 + 4 个肤色**，按 5.6 节的表来。跑通"选一下立刻变"之后再扩量。数量是最后一步，不是第一步。

3. **加一个校准页** `测试/拼装校准.html`：把所有部件一次性叠在同一张网格图上、画出锚点线，一眼就能看出谁没对齐。这是省时间最多的一个文件。

**理由**：把"美术对齐"变成"坐标对齐"，错了能改数值而不是重画。

### R9 连签没有任何出口

**问题**：原稿记了 `连续天数`，但奖励表里没有任何东西用到它——纯装饰，用户不会在意。

**改法**：连签只给**限定装饰**，不给货币：连签 7 天 → 解锁"七天地毯"，14 天 → "半个月挂画"（只能靠连签拿到，不可购买）。

**理由**：给目标感，但不引入"改系统时间刷金币"的动机。**明确写进 PRD：本系统不做防作弊**，连签不含任何货币价值。

## 3. 定稿数值表（施工以本表为准）

```js
var 奖励表 = {
  早:   { 经验: 20, 金币: 5 },
  午:   { 经验: 20, 金币: 5 },
  晚:   { 经验: 20, 金币: 5 },
  喝水: { 经验: 5,  金币: 1 },   // 上限 8 次/日
  运动: { 经验: 30, 金币: 8 },   // 上限 3 次/日
  达标: { 经验: 50, 金币: 20 }   // 一天一次
};

var 每日目标 = { 三餐: 3, 喝水: 6, 运动: 1 };
var 每日上限 = { 喝水: 8, 运动: 3 };

function 升级所需经验(等级) {          // Lv.n → Lv.n+1
  if (等级 >= 10) return Infinity;
  return 100 + (等级 - 1) * 100;       // 100,200,…,900
}
// 累计满级 = 4500；每天满额 230–240 经验 → 约 19–25 天
// 满级后：每 500 经验 +1 星，显示 "Lv.10 ★N"，不影响任何规则
```

**经济自检（写完代码要用 Python 断言）**：
单日金币上限 `5×3 + 1×8 + 8×3 + 20 = 67`；家具满加成 0.35 时约 90。
总价 ≈ 2300 → **约 30–35 天买齐**，且必须满足"满级早于买齐"。

## 5. 渲染方案（定稿）：人物 2D + 房间 3D

### 5.0 为什么这个组合是对的

3D 的死结只在"人"：分件建模 + 骨骼 + 蒙皮，AI 生图给不了（它出 2D 图，不是带权重的模型）。
但**房间恰恰是最容易做 3D 的东西**——地板、墙、桌椅全是规则几何体，程序化生成，一件美术资产都不用。
而人物 2D 分层 SVG 又恰好是"捏脸换装"最容易做好的形式：选一下立刻变、矢量清晰、可测。

> 一句话：**3D 用在不需要美术资产的地方，2D 用在需要大量可换部件的地方**，两边各自避开短板。

### 5.1 零依赖的技术选择：手写 WebGL1，不引入 three.js

| 约束 | 结论 |
|---|---|
| 不许 npm / 打包 / CDN / 在线接口 | 全部满足：shader 源码内联在 JS 字符串里 |
| `file://` 双击可跑 | ✅ WebGL1 从本地页面创建 context，无网络请求 |
| 不引入第三方库 | ✅ 手写约 200 行渲染器，不内置 three.js |

**为什么不内置 three.js**：官方 r150 起弃用 UMD 构建、r160 起移除，新版只发 ESM；而 `file://` 下 `type=module` 会被 CORS 拦。要用就得内置一份 r149 的 600KB UMD——为一个 40 个盒子的静态房间引入第三方库，还得专门开一次范围变更，不划算。

**手写 WebGL1 够不够**：够。只需要 `mat4`（透视、lookAt、平移/缩放/绕 Y 旋转、矩阵乘法）+ 一个带法线的立方体几何 + 一个极简 Lambert 片元着色器（一个方向光 + 环境光）。**不用贴图、不用 glTF、不用阴影贴图**（地面铺一个略深的色块当接触阴影即可）。验证页实测：核心渲染器约 200 行，整页 JS 324 行。

> **硬约束（实测踩到过）**：GLSL 标识符只允许 **ASCII**。项目"函数/变量全中文"的约定**不适用于着色器源码**——
> `attribute / uniform / varying` 及 shader 内局部变量必须写成 `aPosition / uProj / vNormal` 这类英文，
> 写成 `a位置 / 光 / 亮` 会直接编译报 `'?' : syntax error`。这是全项目唯一需要破例用英文命名的地方。

> 备选路线：若手写渲染器调试不过，再走范围变更内置 three r149 UMD。规则层与场景数据都不用改。

### 5.2 两层怎么叠（关键工程决定）

```
┌─ 房间容器 position:relative ────────────────────┐
│  <canvas>          WebGL：地板/墙/家具/光影       │ ← 3D 层，真透视
│  <div class="纸片人"> 内联 SVG 分层拼装            │ ← 2D 层，DOM 叠加
│  <div class="槽位按钮"> 6 个透明点击区             │ ← DOM，不用射线拾取
└───────────────────────────────────────────────┘
```

- **人物用 DOM 叠加，不做 WebGL billboard**：SVG 保持矢量清晰、换装即时；不用把 SVG 转 data URI 纹理（避开 `file://` 下纹理异步加载、CORS、canvas 污染）；省掉整条拾取射线。
- **遮挡关系**：人物固定站在房间前部、永远在最前，不做"家具挡住人"。纸片人立牌 + 3D 场景是成熟做法，观感完全成立。
- **脚下阴影**：CSS 椭圆即可（零成本）；若想更融合，在 3D 地面加一个半透明圆片。
- **槽位交互**：6 个透明 DOM 按钮按投影公式定位在对应家具上方；相机 yaw 限制 ±20° 内，拖动时按钮跟着更新，避免跑到墙后。
- **不持续 `requestAnimationFrame`**：只在拖动、换装、摆家具时重绘一次，省电、不发烫。

### 5.9 真模型路线已跑通（2026-11-16 追加，用户提供 GLB）

用户提供了 Tripo 生成的「男孩玩偶」GLB，于是「人物 2D」这一条被实测改写为**真 3D 模型**。证据：`测试/角色模型验证截图.png`（单模型）、`测试/房间角色合成截图.png`（在房间里）。

源模型：19.5MB，**单网格 229,382 顶点 / 438,618 三角形**，1 张 4096² 贴图，30 根本根骨骼、**无动画**。

**处理链（离线，Python）**：`工具/glb嵌入.py`
1. 剥离 `JOINTS_0 / WEIGHTS_0 / skins / inverseBindMatrices` —— 省 8.7MB；当前只做静态展示，不播骨骼动画；
2. 贴图 4096 → 1024（2.2MB → 0.2MB）；
3. 重建最小 GLB（只留 POSITION / NORMAL / TEXCOORD_0 / u32 索引 / 贴图）；
4. base64 内嵌为 `数据/角色模型.js`（16.2MB）。**运行时不再需要任何转换工具**。

**运行时**：自研最小 GLB 解析（JSON chunk + BIN + accessor）+ 独立贴图着色器。模型不走 `fetch`——`file://` 下会被 CORS 拦，改用 `<script>` 内嵌 base64 后自行解码。

| 验证项 | 结果 |
|---|---|
| base64 解码 12.2MB + 解析 | ✅ 首帧 731ms（软件渲染） |
| WebGL2 / WebGL1 上下文 | ✅ 优先 WebGL2 |
| 贴图上传 GPU | ✅ 1024×1024，glTF UV 不翻转（`UNPACK_FLIP_Y=false`） |
| 在房间里合成 | ✅ 站地毯上、正脸朝镜头、接触阴影 + 呼吸微动 |
| 依赖 | ✅ 仍为零：无 three.js / 无 glTF 库 / 无网络请求 |

**两个必须记住的坑（都已在代码里修掉）**：
1. **u32 索引**：229k 顶点 > 65535，索引只能是 u32。WebGL1 必须 `getExtension("OES_element_index_uint")`，否则 `drawElements` **静默失败——画面全空、控制台不报错**。现在优先取 WebGL2 上下文。
2. **模型正面朝 +X，不是 +Z**：0.62 rad 时看到的是侧脸。面向镜头的朝向常量按 +X 校准（约 −0.85 rad）。

**换装约束（这条会影响 M4 的设计）**：模型是**单一融合网格**，头/发/T恤/裤子/鞋全部烘在同一张贴图里，**没有可拆的衣物网格**。因此「叠层换装」在 3D 人物上不成立，只有三条路：

| 路径 | 做法 | 成本 | 局限 |
|---|---|---|---|
| **A · 贴图染色**（推荐） | 运行时按颜色区域替换贴图（T恤/牛仔裤/鞋各自是清晰色块） | 低，零新资产，秒级换色 | 只能改颜色，不能改款式 |
| **B · 整模替换** | 每套服装单独用 Tripo 生成一个 GLB | 高：每个 12–16MB | 只能整套换，不能混搭；内存与加载压力大 |
| C · 3D 只做人、换装回 2D | 视觉不一致 | — | 不推荐 |

建议 **A 为主 + B 少量精品（3–5 套）**；捏脸同理——染色 + 可选替换发型模型，不做滑块。

**体积警告**：单角色 16.2MB。真要多套服装，必须让 Tripo 导出**低模**（减面到 5 万面以内），否则 5 套就是 80MB+，双击打开会明显卡。

### 5.10 家具 GLB 与「保留骨骼」的实测（2026-11-16 追加）

用户又提供了「迷你客厅」GLB，并决定**保留骨骼**。两个结论都改变了实现细节。

**（1）迷你客厅只有家具，没有房间**

13.5MB / 219k 顶点 / 411k 三角形 / 无骨骼。内容是一整套家具：书桌（带笔电、书、抽屉）、书架（带相框、绿植）、绿色单人沙发、落地灯、盆栽。**没有墙、没有地板**，而且**六件家具是一个融合网格**。

结论：
- 房间壳（地板 / 两面墙 / 踢脚 / 地毯）继续由程序生成——这部分反而最不该换模型，因为墙纸、地板颜色是要按商店卖的；
- 家具**不能按槽位拆分替换**。要么整组当固定陈设，要么让 Tripo 一件一件单独生成 GLB（每件一个模型才能换）。

**（2）保留骨骼后，蒙皮有四个坑（全部已在 `测试/真房间合成.html` 修掉）**

角色模型转成保留骨骼后 23.2MB（含 JOINTS_0 / WEIGHTS_0 / 30 关节 / 45 节点 / 绑定逆矩阵）。

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | u16 访问器漏乘分量数 | 关节索引整体错位，**画面看着正常但怎么转都不动** | `Uint16Array(count × 分量数)`，VEC4 必须 ×4 |
| 2 | 骨骼节点 TRS 被抹平 | 顶点头、四肢被揉成一团碎片 | 从 `inverseBindMatrices` 反推：绑定全局 = inverse(IBM)，绑定局部 = inverse(父绑定全局)·绑定全局 |
| 3 | 关节链被非关节节点截断 | 转肩膀，手臂完全不动（Twist 骨成了孤立根） | 父链要一路向上追溯，直到最近**关节**祖先 |
| 4 | 骨骼局部轴沿骨头方向 | 直接转等于「拧」，看不出抬手 | 绕**世界轴**、以该关节绑定位置为支点旋转 |

另有一条经验：**不要相信关节名**。Tripo 导出的 `skin.joints` 里没有 `R_Upperarm` / `R_Forearm`，只有 `R_UpperarmTwist01/02`、`R_ForearmTwist01/02`——按「实际存在的关节」取名，否则拿到的索引是 −1，姿势静默失效。

**（3）当前性能账（必须是清醒的）**

| 项目 | 数值 |
|---|---|
| 数据体积 | 角色 23.2MB + 家具 15.4MB = **38.6MB** 的 JS |
| 三角形 | 438k + 411k = **849k** |
| 首帧（软件渲染） | **约 11 秒** |
| 真机 GPU | 会快很多，但「双击打开」的等待仍然存在 |

**这一步的结论**：玩法必须先做成「有没有模型都能玩」，模型只是渲染层的替换品；否则一旦资产过重，双击打开就卡死，作品没法演示。

**这一层踩到的两个真坑（已修，都有断言）**：

1. **不能用「结果」字段判断成败**：`结算打卡` 在新打卡成功时也返回 `"已完成"`（和"重复打卡"同一个字符串）。判据必须是「本次有没有真的得分」（`获得.经验 + 获得.金币 > 0`），否则第一次打卡不落盘。
2. **`每日` 必须无条件落盘**：只在得分时写，会让换天后的第一次失败操作（重复 / 未到餐点）把昨天的三餐留在存储里。事实型状态（今天做了什么）跟日历走，奖励型状态（经验 / 金币 / 流水）才看得分。
