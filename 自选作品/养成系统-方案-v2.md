# 养成系统 · 方案 v2（评审稿）

日期：2026-11-16 ｜ 目标作品：`自选作品/`（食谱搭配 v0.5.0，7 页纯前端、零依赖、断网可跑）
基础稿：`养成系统-实现规格.md`（DeepSeek 版 v0.6.0）
本文件只做三件事：**判断原稿能不能用 → 列出必须改的地方 → 回答 3D 可行不可行**。
定稿后由执行者按本文件的数值施工，原稿仍然有效（除被本文件覆盖的条目）。

---

## 0. 结论摘要

1. **原稿骨架是对的，可以直接用**：纯函数分离、奖励只看打卡不看卡路里、不惩罚断签、先规则后 UI、Python 对拍——这几条判断都对，而且和这个项目的工程纪律吻合。不需要推翻重来。
2. **但有 8 处会真实翻车的地方必须改**（第 2 章），其中 2 处是"用户正常操作就吃亏"的 bug，1 处是"5 分钟刷满一天"的漏洞，1 处是最大的落地风险（SVG 拼装）。
3. **数值要重算**：原稿 19 天满级 vs 60 天买齐，节奏是错位的；达标线=上限（喝水 8/8）会让"达标"变成"打满"。
4. **手机端会失去全部反馈**：原稿在 ≤900px 直接隐藏经验条，而手机是最可能的使用场景。
5. **3D：能做，但不建议把"换装角色"做成 3D**。推荐 2.5D 等距方案（零依赖、无新资产风险、视觉已有"游戏感"），并把场景数据结构设计成可被 3D 渲染器直接接管。详见第 5 章。

## 1. 原稿值得保留的部分（不要再讨论）

| 决定 | 为什么保留 |
|---|---|
| 经验只看"餐次有没有打卡"，完全无视卡路里 | 一旦卡路里参与奖励，用户会为了升级少吃；且与已有 1200 kcal 下限保护自相矛盾 |
| 断签只归零连签，不扣经验/等级/物品 | 惩罚机制在养成系统里性价比极低，断签的人本来就在弃用边缘 |
| 喝水 8 次 / 运动 3 次封顶 | 防止"为了经验瞎喝水" |
| 规则全部写成不碰 DOM 的纯函数，Python 对拍 | 环境没有 Node，这是唯一可自动化验证的路 |
| 只挂一个入口（`添加记录`），不新开记录通道 | 用户不用多学一套；也避免同餐双记 |
| 商店塞进换装抽屉，不做第 8 个侧栏项 | 导航密度已到上限，"买→穿"是同一个动作 |
| 养成出错必须 `try/catch` 包住，绝不影响记录 | 记录是主线，养成是附加 |

## 2. 必须改的 8 处（问题 → 改法 → 理由）

### R1 22 点后吃晚饭，永远拿不到"晚"的经验（bug）

**问题**：`判定餐次()` 是 `<21` 才返回"晚"，21 点后返回"加餐"；而原稿规定"加餐不计三餐"。结果是**晚睡的人只要 21 点后记录晚餐，就永远不可能达标**，且当天少 20 经验。这不是边界情况，是常见作息。

**改法**：养成侧不看"加餐"这个标签，做一次兜底：
- 来源为"加餐"且 `每日.三餐` 里还没有"晚" → **记为"晚"**（当天仅一次）；
- 来源为"加餐"且"晚"已记 → 忽略，不给经验、不提示。

**理由**：21 点后那一餐，用户语义上就是晚饭。兜底一次即可，不会变成无限刷。

### R2 计划页"标记已吃"可以让三餐在 5 分钟内刷满（漏洞）

**问题**：`标记计划已吃()` 会把 `餐.餐次` 直接传给 `添加记录`，餐次来自计划本身，**与当前时间无关**。早上 8 点就能把计划里的"晚餐"标成已吃，于是 8:03 就能凑满三餐 + 达标 ≈ 240 经验。演示时被问到会很尴尬。

**改法**：挂载点带一个"是否强制餐次"标记，并加**餐次时间窗**：
- 强制餐次（计划页）且在窗口内 → 正常计经验；不在窗口内 → 记录照写，但 `结果='未到餐点'`、获得 0；
- 非强制（记录页/总览页，餐次由当前时间自动判定）→ 不校验窗口。

| 餐次 | 时间窗 |
|---|---|
| 早 | 04:00–09:59 |
| 午 | 10:00–14:59 |
| 晚 | 15:00–03:59（跨零点，指"今天这一顿晚饭"） |

**理由**：允许提前一点（15:00 记晚饭是正常的），但不允许把一天压缩成 5 分钟。

### R3 达标线 = 上限，等于没有达标线

**问题**：原稿"达标"要求喝水 8 杯，而喝水上限也是 8 杯。也就是说必须**打满**才算达标，实际大部分人拿不到那 50 经验，`是否刚达标` 长期为 false，达标徽章变成摆设。

**改法**：**达标线低于上限**——`每日目标 = { 三餐: 3, 喝水: 6, 运动: 1 }`，上限仍是 8 / 3（多喝多练仍有经验，但不再影响达标）。

**理由**：目标要留余量，这是行为设计常识；6 杯（约 1.5L）也是更现实的日常量。

### R4 经济节奏错位：19 天满级，60 天才买齐

**问题**：原稿算下来一天满额 67 金币，全部装扮 + 家具约 4000+ 金币 → 约 60 天。结果：**19 天满级后进入"什么目标都没有"的空窗期**，收集曲线比等级曲线慢 3 倍。

**改法**（两条一起做）：

1. **重定价**，把总价压到约 2200–2400：

| 分类 | 数量 | 免费 | 价格区间 |
|---|---|---|---|
| 发型 | 8 | 2 | 20–60 |
| 上衣 | 10 | 2 | 30–80 |
| 裤子 | 8 | 2 | 25–60 |
| 鞋 | 6 | 2 | 15–50 |
| 配饰 | 6 | 2（含 `饰-无`） | 40–90 |
| 家具 | 6 | 0 | 60–150 |

约束：**任何单件 ≤ 3 天收入（≈200 金币）**，不能出现"看着买不起"的货。

2. **满级后接星星**：`Lv.10` 之后经验继续累积，每 500 经验 +1 星（显示 `Lv.10 ★3`），不新增任何系统。

**理由**：让**满级（约 19–25 天）早于买齐（约 30–35 天）**，满级后仍有"差两件没凑齐"的牵引，而不是满级即弃。

### R5 手机上没有任何经验反馈

**问题**：原稿写"≤900px 侧栏转顶部导航时，养成块隐藏"。但记录动作在手机上同样发生，**反馈被藏起来的反馈等于没有反馈**——这恰好违反原稿自己在第 14 章写的第 6 条理由。

**改法**：≤900px 时，把养成块压缩成**顶栏右侧胶囊**：`Lv.3 · 320/500 · 42` （等级 · 经验 · 金币），点击进养成页；进度用胶囊底部的 2px 细条表示。

**理由**：占位极小，但"涨了"看得见。

### R6 存档只有一份，且不可迁移（最大的用户损失风险）

**问题**：全部资产在 `localStorage`，一次"清除浏览数据"或者换电脑，形象、宠物、连续天数全没。养成系统与普通数据不同——**用户对宠物和形象有情感投入，丢了就是差评**。原稿完全没处理。

**改法**（成本很低）：
- 养成页底部加「存档」：**导出**（把 `食谱搭配-养成*` 三个键序列化成一段文本放进 `<textarea>`，用户自己复制走）+ **导入**（粘贴文本 → 校验版本与字段 → 覆盖）。不写文件、不联网、不弹窗。
- 导入必须**先校验再写**：结构不对就整段拒绝并提示，绝不半覆盖。

**理由**：纯前端做不到云同步，但"用户可以自己备份"能挡住 90% 的丢失场景，也顺便给了"换设备"一个说法。

### R7 冗余字段会漂移

**问题**：`今日获得经验` 是缓存字段。一旦某次写入失败或跨标签并发，它就和流水对不上，最后没人知道哪个是真的。

**改法**：删掉该字段，`今日获得` 一律**从流水按日期求和**（流水只留 30 条、每天最多 15 条，够用）。

**理由**：同一个事实只存一处。

### R8 SVG 拼装没有坐标契约（最大的落地风险）

**问题**：原稿要求"每个部件一层 `<g>`，按当前形象拼进 `viewBox 0 0 200 320`"，但**没有规定任何锚点/坐标带**。实际施工时，衣服必然对不上身体——手写的 38 个部件 × 5 层叠加，靠肉眼一件件调到对齐，是最容易做到崩溃的一步，而且改一件要重调全部。

**改法**（三条）：

1. **写死坐标带**（所有部件都在同一画布绝对定位，不用 `transform`）：

| 部位 | 坐标带（y） | 锚点 |
|---|---|---|
| 头发 / 头饰 | 24–112 | 头顶 y=30，头心 y=68 |
| 上衣 | 108–212 | 肩线 y=120，下摆 y=208 |
| 裤子 | 196–292 | 腰线 y=204 |
| 鞋 | 278–314 | 脚底线 y=312 |
| 配饰 | 96–140（项链）/ 24–70（帽子） | 颈点 y=100 |

   图层顺序固定：`身体 → 裤子 → 鞋 → 上衣 → 头发 → 配饰`。

2. **首版减量**：先做 发型 4 / 上衣 5 / 裤子 4 / 鞋 3 / 配饰 3 = **19 件**，跑通"穿上立刻变"之后再扩到第 R4 表的数量。数量是最后一步，不是第一步。

3. **加一个校准页** `测试/拼装校准.html`：把所有部件一次性叠在同一张网格图上、画出锚点线，一眼就能看出谁没对齐。这是省时间最多的一个文件。

**理由**：把"美术对齐"变成"坐标对齐"，错了能改数值而不是重画。

### R9 连签没有任何出口

**问题**：原稿记了 `连续天数`，但奖励表里没有任何东西用到它——纯装饰，用户不会在意。

**改法**：连签只给**限定装饰**，不给货币：连签 7 天 → 解锁"七天地毯"，14 天 → "半个月挂画"（只能靠连签拿到，不可购买）。

**理由**：给目标感，但不引入"改系统时间刷金币"的动机。**明确写进 PRD：本系统不做防作弊**，连签不含任何货币价值。

### R10 规范自身的不一致（施工前先改掉）

| 位置 | 冲突 | 定稿 |
|---|---|---|
| 第 5.2 / 7.2 节 | 一会儿"6 个 HTML 全加"，一会儿 7 页 | **7 页全加**（新增的 `养成.html` 也有侧栏）；`检查契约.py` 覆盖 7 页 |
| 4.1 vs 4.2 | 一处说满级需 4300，一处算 4500 | **4500**（100+200+…+900） |

## 3. 定稿数值表（施工以本表为准）

```js
var 奖励表 = {
  早:   { 经验: 20, 金币: 5 },
  午:   { 经验: 20, 金币: 5 },
  晚:   { 经验: 20, 金币: 5 },
  喝水: { 经验: 5,  金币: 1 },   // 上限 8 次/日
  运动: { 经验: 30, 金币: 8 },   // 上限 3 次/日
  达标: { 经验: 50, 金币: 20 }   // 一天一次
};

var 每日目标 = { 三餐: 3, 喝水: 6, 运动: 1 };
var 每日上限 = { 喝水: 8, 运动: 3 };

function 升级所需经验(等级) {          // Lv.n → Lv.n+1
  if (等级 >= 10) return Infinity;
  return 100 + (等级 - 1) * 100;       // 100,200,…,900
}
// 累计满级 = 4500；每天满额 230–240 经验 → 约 19–25 天
// 满级后：每 500 经验 +1 星，显示 "Lv.10 ★N"，不影响任何规则
```

**经济自检（写完代码要用 Python 断言）**：
单日金币上限 `5×3 + 1×8 + 8×3 + 20 = 67`；家具满加成 0.35 时约 90。
总价 ≈ 2300 → **约 30–35 天买齐**，且必须满足"满级早于买齐"。

## 5. 3D 能不能做（重点）

先把问题拆开：用户说的"3D"其实是三个不同的东西，成本差 10 倍。

| 想要的东西 | 能不能做 | 难度 |
|---|---|---|
| ① 小窝/房间有立体感，家具能摆 | **能，而且好看** | 中 |
| ② 形象是 3D 小人，换衣服看得到 | 技术能，美术不能 | **极高** |
| ③ 能自由走动、转视角的漫游 | 能，但没必要 | 高（且和"打卡"玩法无关） |

**②是死结，原因不在代码在资产**：3D 换装要求每件衣服都是独立网格、共享同一套骨骼、UV 与权重都对得上。AI 生图给不了这个（它出的是 2D 图，不是带蒙皮的模型）。手写几何体拼出来的小人会像 90 年代的方块人。要做只能进 Blender 建 40 件分件模型并绑定——这不是这个作品该花的时间。

### 5.1 三档方案对比

| | **A · 2D 分层 SVG**（原稿） | **B · 2.5D 等距**（推荐） | **C · 真 3D（WebGL）** |
|---|---|---|---|
| 渲染方式 | 内联 SVG 分层拼装 | CSS 3D 透视 + 等距精灵 + 视差 | three.js 固定等距相机 |
| 新增依赖 | 无 | 无 | 内置一份 three UMD，约 600KB |
| `file://` 双击 | ✅ | ✅ | ⚠️ 只能 UMD；ESM 版在 `file://` 下被 CORS 拦 |
| 形象换装 | ✅ 简单 | ✅ 简单（纸片人立牌） | ❌ 需分件建模 + 骨骼 |
| 房间家具 | 平面九宫格 | ✅ 可拖拽、有前后遮挡、有视差 | ✅ 真阴影、自由摆位 |
| 美术成本 | 中（38 件手写 SVG） | **中低**（AI 生等距素材 + 少量手写） | 极高 |
| 视觉惊喜 | 一般 | **高**（倾斜一点就"活"了） | 最高 |
| 纯函数可测性 | ✅ | ✅（渲染层分离） | ✅（渲染层分离） |
| 翻车风险 | 低 | 低–中 | **高**（资产、旧电脑集显、时间） |
| 课程演示 | 稳 | 稳且有亮点 | 可能很惊艳，也可能卡成 PPT |

### 5.2 结论：选 B，但架构上给 C 留门

**推荐 B（2.5D 等距）**，具体做法：

1. **房间**：一张等距小房间背景（AI 生成，转成本地 PNG，和现有"动作图片"同一套做法）+ 6 个家具位。家具用透明底等距精灵，带投影。
2. **立体感**：容器加 `perspective` + `rotateX(6deg)`，鼠标移动做 ±3° 的视差倾斜；家具按 `y` 排序决定前后遮挡。
3. **形象**：仍是 2D 分层 SVG（R8 的坐标带），但站在房间里当"立牌"，加**呼吸、眨眼、轻微摇摆**三个 CSS 动画 + 脚下椭圆阴影。人对"活"的感知来自动效，不是维度。
4. **代价**：与 A 相比只多一层渲染，规则、存档、测试**完全不变**。

**给 C 留门的方式**（很关键）：把"场景"抽成纯数据，渲染层只读它。

```js
// 食谱搭配-养成场景（与渲染方式无关）
{ "地板": "木地板", "墙纸": "米白",
  "家具": [ { "槽": 0, "id": "家具-木桌", "x": 0.32, "y": 0.58, "翻转": false }, ... ] }
```

2.5D 用它摆精灵；将来换 three.js 就把同一份 `x/y` 当世界坐标喂给相机投影，**规则和存档一行不改**。这样"以后要不要上真 3D"就变成一个纯渲染决策，不再是重写。

### 5.3 如果确实要真 3D，最小可行范围

只做 **房间**，不做换装角色：

- 内置 three r14x **UMD** 构建（r150 起官方弃用、r160 起移除，新版只发 ESM，而 `file://` 下 module 脚本会被 CORS 拦）；
- 固定等距相机，**不做自由漫游**（漫游对"打卡"没有增益，只增加 bug）；
- 家具用程序化几何（Box / Cylinder）+ 纯色材质，不用贴图（贴图要么外链要么 base64，都不划算）；
- 角色是 `PlaneGeometry` + canvas 贴图（由现有 SVG 转 data URI），永远面向相机（billboard）；
- 放在 M6，作为可选里程碑：**前面的东西全部做完再动**，做不成直接回退到 B，不影响任何已交付功能。

## 8. 需要你定的三件事

1. **视觉档位**：A（纯 2D）/ **B（2.5D 等距，推荐）** / C（真 3D 房间）。选 B 的话，M5 做完就能演示，M6 上不上都不影响交付。
2. **"每个人"的含义**：如果指"同一个浏览器里几个人各养各的"，可以加**3 个存档槽**（切换档位，共用一个键，成本不大）；如果只是"每个使用者自己"，那现在这样天然就是每人一套，只是不能跨设备（靠 R6 的导出/导入兜）。
3. **形象是否只做"部件换装"**：不做上传头像 / 捏脸滑块。原因是上传需要图片存储与尺寸处理，捏脸画不出稳定效果。这一条建议直接写进"不做"清单。
