# PRD · 食谱搭配网页

版本：v0.3.0 ｜ 更新日期：2026-11-13 ｜ 状态：饮食/训练双分区 + CookHero 式饮食管理 + 可选 AI 助手

---

## 一、一句话描述

一个网页：用户填身体数据得到每日目标卡路里，按人群选择并打卡食谱，系统根据剩余额度自动推荐下一餐；
另设训练分区，按部位提供健身动作教程（姿势与要点）。

## 二、用户是谁

- 主要用户：想简单管理每日饮食与基础训练的大学生（本课程同学）。
- 使用场景：
  - 饮食：中午吃完饭后打开网页记录一下，看今天还剩多少额度、晚上该吃什么。
  - 训练：练之前查一下目标部位有哪些动作、每个动作的姿势要点和常见错误。

## 三、输入 / 处理 / 输出（IPO）

| 环节 | 内容 |
|---|---|
| **输入** | ① 身体数据：性别、年龄、身高、体重、活动量、人群 <br> ② 今日已吃：从食谱列表里点选 |
| **处理** | ① 三步公式算出每日目标卡路里 <br> ② 累加已记录食谱的五类营养 <br> ③ 按「剩余额度 + 人群标签」排序推荐 |
| **输出** | 目标卡路里、今日已摄入 / 剩余、五类营养合计、3 道推荐食谱 |

## 四、验收条件（A1 用的就是这个）

> 用户打开网页 → 填写身体数据并点击「计算目标」→ 页面显示一个每日目标卡路里 →
> 从「全部食谱」点几道菜「记录」→ 上方卡路里数字增加、进度条变长 →
> 当已摄入超过目标时，进度条变红 →
> 下方「为你推荐」列出 3 道属于当前人群、且今天还没吃过的菜。

以上每一步都能肉眼观察，不需要任何人解释。

## 五、核心规则（写死的，不做可选）

### 5.1 人群（固定 4 类）

减脂 / 增肌 / 控糖 / 均衡。不做自定义人群，不做问卷测试。

### 5.2 每日目标卡路里：三步计算

**第一步 · 基础代谢 BMR（Mifflin-St Jeor 公式）**

- 男：`BMR = 10 × 体重(kg) + 6.25 × 身高(cm) − 5 × 年龄 + 5`
- 女：`BMR = 10 × 体重(kg) + 6.25 × 身高(cm) − 5 × 年龄 − 161`

**第二步 · 乘活动系数得到每日消耗 TDEE**

| 活动量 | 系数 |
|---|---|
| 久坐（几乎不运动） | 1.2 |
| 轻度（每周1–3次） | 1.375 |
| 中度（每周3–5次） | 1.55 |
| 高度（每周6–7次） | 1.725 |

**第三步 · 按人群微调**

| 人群 | 系数 |
|---|---|
| 减脂 | × 0.8 |
| 增肌 | × 1.1 |
| 控糖 | × 1.0（不增减） |
| 均衡 | × 1.0（不增减） |

**固定边界**

1. 结果**取整到 10 kcal**：`round(值 / 10) × 10`。
2. 取整后若 `< 1200`，显示 **1200**，并提示「目标过低，已自动上调」。
3. 下限判断放在取整**之后**。

**标准示例（用作回归测试用例）**

> 22 岁女性，165 cm，55 kg，久坐，减脂：
> `BMR = 10×55 + 6.25×165 − 5×22 − 161 = 1310.25`
> `TDEE = 1310.25 × 1.2 = 1572.3`
> `减脂 = 1572.3 × 0.8 = 1257.84` → 取整到 10 → **1260 kcal**

### 5.3 食谱字段契约（所有食谱必须一模一样）

| 字段 | 类型 | 单位 | 规则 |
|---|---|---|---|
| id | 字符串 | — | 唯一，格式 `r` + 三位数字 |
| 名称 | 字符串 | — | 非空 |
| 人群 | 字符串数组 | — | 至少 1 个；只能取「减脂/增肌/控糖/均衡」 |
| 卡路里 | 整数 | kcal | 0 ≤ 值 ≤ 3000 |
| 碳水 | 数字 | g | ≥ 0，保留 1 位小数 |
| 脂肪 | 数字 | g | ≥ 0，保留 1 位小数 |
| 膳食纤维 | 数字 | g | ≥ 0，保留 1 位小数 |
| 蛋白质 | 数字 | g | ≥ 0，保留 1 位小数 |
| 食材 | 字符串 | — | 非空；食材清单（v0.2 新增） |
| 步骤 | 字符串数组 | — | 非空数组，每条一个做法步骤（v0.2 新增） |
| 图片 | 字符串 | — | 本地相对路径 `数据/图片/<id>.jpg`；空字符串表示暂无配图 |

固定规则：

1. 字段名固定，绝不混用（不写 `kcal`、`Calorie`、`carbs`）。
2. 数字只写数字，不带单位（写 `420`，不写 `"420 kcal"`）。
3. 卡路里为整数；其余四项固定保留 1 位小数（写 `9.0`，不写 `9`）。
4. 五类营养**必须齐全**，缺任一字段即视为无效数据。
5. 图片**必须本地化**，禁止外链，保证断网可用。

### 5.4 推荐规则

1. 只从**当前人群标签**里挑。
2. 今天**已经记录过的菜不再推荐**。
3. 每餐预算 ≈ 剩余额度 ÷ 3，选卡路里最接近预算的。
4. 同分时按人群偏好加分：减脂看蛋白/脂肪比，增肌看蛋白，控糖看低碳水 + 高纤维。
5. 剩余 ≤ 100 kcal 时不再推荐，显示「今日已达目标额度」。

### 5.5 一周食谱计划规则

1. **固定 7 天**，每天最多三餐（早 / 午 / 晚）。界面上不提供 30 天选项。
2. 逐日扣减额度：每餐预算 = 当日剩余额度 ÷ 剩余餐数。
3. 从「当前人群 + 本周未用过 + 当天未用过 + 单餐不超剩余额度」的候选里，
   选卡路里最接近餐预算的。
4. 本周可选项用尽时，允许跨天重复，但**同一天内仍不重复**。
5. 单餐卡路里**不得超过当日剩余额度**，避免出现「预算 40 却推 160」的情况。
6. 计划存入 localStorage，键名 `食谱搭配-一周计划`，可清除重生成。

### 5.6 食谱专区（按人群分区）

1. 分区：全部 / 减脂 / 增肌 / 控糖 / 均衡，显示各分区食谱数量。
2. 每条食谱以卡片展示：图片位、菜名、人群标签、五项营养、卡路里、记录按钮。
3. **图片字段**：`菜.图片` 指向 `数据/图片/<id>.jpg` 本地文件，**断网也能显示**。
   为空字符串时显示占位块（图标 + 无障碍标签），加载失败自动退回占位块。
   不允许使用外链（测试会拦截 `http://` / `https://` 开头的图片路径）。
4. 当前 40 条食谱**全部有配图**。其中 r001–r024 的 24 张来自 Unsplash（遵循 Unsplash License）
   或课程作业专用素材；r025–r040 的 16 张为 AI 生成配图（2026-11-13，供本课程作品使用），
   菜品内容参考《减脂饮食全书》（github.com/da-damu/fat-loss-diet-book）。
   来源均注明于 README。

### 5.7 页面分区结构（v0.2 新增）

页面顶部设**主功能分区导航**，两个分区独立切换、互不干扰：

| 分区 | 内容 | 说明 |
|---|---|---|
| 🥗 饮食 | ① 设置目标 ② 今日摄入 ③ 为你推荐 ④ 食谱专区 ⑤ 一周计划 + 今日已记录 + ⑥ AI 助手（可选） | 原有全部饮食功能 |
| 💪 训练 | 健身动作教程 + 安全说明 | v0.2 新增 |

设计要点：

1. 两个分区各自是独立的 `<div class="功能区">`，切换时用 `hidden` 属性控制显隐。
2. 当前分区记入 `localStorage`（键名 `食谱搭配-主分区`），刷新后保持。
3. 分区内各自有二级导航（饮食按人群、训练按部位），互不影响。

### 5.8 健身动作教程（v0.2 新增）

**动作字段契约**

| 字段 | 类型 | 规则 |
|---|---|---|
| id | 字符串 | 唯一，格式 `e` + 三位数字 |
| 名称 | 字符串 | 非空 |
| 部位 | 字符串 | 只能取「上肢 / 下肢 / 核心 / 全身」 |
| 目标肌群 | 字符串 | 非空 |
| 要点 | 字符串数组 | **3–5 条** |
| 常见错误 | 字符串数组 | **1–3 条** |
| 建议 | 字符串 | 组数 × 次数/时长 |
| 图片 | 字符串 | 本地相对路径 `数据/动作图片/<id>.jpg`；空串表示用内置示意图 |

**分区与内容**

1. 部位分区：全部 / 上肢 / 下肢 / 核心 / 全身，显示各部位动作数量。
2. 每个部位至少 2 个动作；当前共 14 个（上肢 4、下肢 3、核心 4、全身 3）。
3. 每张动作卡展示：图片位、动作名、建议组次、目标肌群、动作要点、常见错误。

**示意图机制**

找不到准确照片的动作**不放错图**，改用内置 SVG 简笔示意图（按部位区分姿态剪影）。
当前 10 个动作有实拍照片，4 个（深蹲、弓步蹲、平板支撑、侧支撑）使用示意图。

**安全边界（重要）**

1. 页面明确声明：内容为通用健身参考，**不构成专业教练指导或医疗建议**。
2. 有伤病、心血管疾病、孕期等特殊情况，提示先咨询医生或专业教练。
3. 不做动作识别、不做实时纠正——本版本不接摄像头。

### 5.9 数据存放

- 食谱数据：`数据/食谱.js`（由 `数据/foods.json` 转换，便于本地双击打开时免跨域读取）。
- 动作数据：`数据/动作.js`。
- 用户记录与目标：浏览器 `localStorage`，键名 `食谱搭配-今日记录` / `食谱搭配-今日目标`。
- 一周计划：`食谱搭配-一周计划`。
- 当前主分区：`食谱搭配-主分区`。
- AI 助手设置（接口地址 / 模型 / 密钥）：`食谱搭配-AI设置`（v0.3，密钥只存本浏览器）。
- **不做**后端、不做账号、不做云同步。

## 六、三不原则（本项目当前绝不做的三件事）

> 本版本 v0.1 **明确不做**，不是"以后再说"，是当前范围外：

1. **不做**账号注册、云端同步、多用户。
2. **不做**花哨的可视化图表（环形图、趋势曲线、柱状图对比等）。
3. **不做**一个月（30 天）的食谱计划。

**为什么**：这三件事都会让项目在两周内变成做不完的焦油坑。先把「算目标 → 记一天 → 推荐下一餐」和「查动作 → 学要点」这两条主链路做扎实。

**逐条理由**：

| 条 | 拒绝场景 | 为什么拒绝 |
|---|---|---|
| 1 | 「能不能同步到手机 / 加个登录」 | 一旦有账号就有服务器、权限、隐私合规，作品从本地工具变成半个产品 |
| 2 | 「进度条太朴素了，加个环形图 / 趋势曲线吧」 | 一个进度条已把「还剩多少」说清楚；多一种图表就多一类空数据与极端值边界。属第 8 周《画蛇添足》典型陷阱 |
| 3 | 「能不能直接排一个月的食谱？」 | 一个月等于 90 餐，需要处理重复、口味疲劳、食材浪费；7 天已足够暴露问题，30 天只是把同样的逻辑拉长，收益低而返工多 |

**怎么用**：以后有人（包括 AI）建议加这三类功能，直接引用本节，在 Issue 里写明「超出当前三不原则」，推迟到后续版本。

## 八、已知限制

1. 营养数据为教学用估算值，**不构成医学或营养建议**。
2. 只保存同一天记录，不保留历史（换天不自适应，属第3条三不原则）。
3. 推荐只做简单排序，不考虑口味偏好、过敏原、烹饪时间。
4. 需要在现代浏览器中打开（Chrome / Edge），不支持 IE。
5. **核心数据完全离线**：40 条食谱写死在 `数据/食谱.js` 中，不调用任何在线营养数据库；
   所有核心数据均可人工核对。**唯一联网的部分**是 v0.3 的可选 AI 助手（见 5.13）：
   需自备密钥、可在设置中关闭，不配置时全部功能离线可用。
6. AI 助手的营养估算由大模型生成，**精度有限且不稳定**，仅供教学演示对比，
   不作为记录与推荐的主数据源（主数据源始终是本地 40 道菜）。

### 5.10 食材与做法（v0.2 新增，借鉴 CookHero 菜谱查询）

1. 每条食谱带「食材」（字符串）与「步骤」（字符串数组，3–5 条）。
2. 食谱专区的卡片有「做法」按钮，展开显示食材清单与编号步骤，默认收起。
3. 新增菜品（r025–r040）的做法参考《减脂饮食全书》整理；既有 24 道菜为人工补写。

### 5.11 餐次与「标记已吃」（v0.2 新增，借鉴 CookHero 计划 → 记录闭环）

1. 点「记录」时按当前时间自动归入餐次：< 10 点为早，< 15 点为午，< 21 点为晚，其余为加餐。
2. 「今日已记录」列表中每条显示所属餐次标签。
3. 一周计划的第 1 天视为今天：每餐有「标记已吃」按钮，点击后该餐转入今日记录（按计划餐次归档），
   按钮变为「已吃 ✓」徽章。标记状态存入一周计划存档的 `已吃` 数组。

### 5.12 宏量营养目标与偏差分析（v0.2 新增，借鉴 CookHero 目标管理 / 营养分析）

1. 目标卡路里按人群供能比换算出蛋白质 / 脂肪 / 碳水三项目标（克）：
   减脂 30/25/45，增肌 25/25/50，控糖 25/35/40，均衡 20/30/50（蛋白质/脂肪/碳水）。
2. 换算公式：目标克数 = round(目标卡路里 × 供能比 ÷ 每克供能)，每克供能：蛋白质 4、脂肪 9、碳水 4。
3. 「今日摄入」面板在设置目标后显示三项目标值（如「g / 目标 95」）。
4. 生成一周计划后，在计划区显示**一句话文字偏差分析**：今天（第 1 天）计划合计 vs 实际记录，
   多/少约多少 kcal。**只做文字，不做图表**（见三不原则第 2 条）。

### 5.13 AI 助手（v0.3 新增，可选功能，需联网）

> 借鉴 CookHero 的 AI 记录 / 营养分析 / 个性化推荐理念，由项目所有者于 2026-11-13
> 主动要求接入真实大模型（此前仅做本地规则版）。**定位是可选增强，不是必选项。**

**三个子功能**

| 子功能 | 输入 | 输出 | 降级行为 |
|---|---|---|---|
| AI 记录 | 一句话描述（如「中午吃了一碗牛肉面」） | 估算营养后写入今日记录（id 前缀 `AI`，人群为空） | 解析失败不写入，提示重试 |
| AI 营养分析 | 今日记录 + 目标 + 宏量目标 | 不超过 120 字的文字短评 | 提示失败原因，规则版偏差分析仍在 |
| AI 个性化推荐 | 人群 / 宏量缺口 / 剩余额度 / 40 道菜清单 | 最多 3 道菜 + 每道一句理由 + 总评 | 校验不过的候选项直接丢弃，规则推荐（③）仍在 |

**硬性边界（与零依赖约束的受控折衷）**

1. **核心功能仍完全离线**：不配置密钥或断网时，AI 功能给出提示并停用，
   记录 / 推荐 / 计划 / 训练等其余功能不受任何影响。
2. **密钥安全**：密钥只存浏览器 `localStorage`（`食谱搭配-AI设置`），不写进代码、
   不进 Git 仓库（仓库公开）；页面提供 password 输入框填写。
   `测试/逻辑复算.py` 有静态检查项，拦截代码里的疑似密钥字面量。
3. **接口标准**：OpenAI 兼容 `/chat/completions`，默认 DeepSeek（模型 `deepseek-flash`，
   `deepseek-chat` 已于 2026-09 下线），接口地址与模型名均可在页面设置里更换，
   不引入任何第三方库（原生 `fetch`）。调用 DeepSeek 时自动带
   `{"thinking":{"type":"disabled"}}` 关闭思考模式（默认开启会明显增加延迟与费用；
   其他服务商不加该字段，避免参数不识别报 400）。
   地址自动补全：填域名或带路径的 base 均可，页面会拼上 `/chat/completions`；
   设置里有「测试连接」按钮，把网络不通 / 密钥无效 / 一切正常三种情况区分开。
   **服务商浏览器直连兼容性（2026-11-13 实测）**：DeepSeek ✅、Kimi/Moonshot ✅、
   通义 DashScope 兼容模式 ✅（均允许 `file://` 页面直连）；智谱 BigModel ❌ 不放行
   浏览器跨域（报 `Failed to fetch`），暂不可用——此为服务商行为，纯前端无法绕过。
4. **返回值不信任**：AI 返回的 JSON 必须通过 `校验AI菜品` / `校验AI推荐`（区间、
   id 存在性、已吃剔除、额度上限、去重）才生效，宁可少推不硬推。
5. **隐私与免责**：使用 AI 功能时，今日记录摘要会发送给你自行选择的大模型服务商；
   AI 输出为教学演示性质的估算，不构成营养或医学建议（提示词中已约束）。
6. AI 输出**只有文字**，不做图表（守三不原则第 2 条）；不做账号体系（守第 1 条）。
